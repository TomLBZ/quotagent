# 实现陷阱（门/流程/文档）

> 运行时侧（宿主/桥/shell）的陷阱在 [`pitfalls-runtime.md`](pitfalls-runtime.md)。

- **单价与数量的换算方向相反**：把"每 cm 的价格"换到基准单位 m 要乘**倒数因子**（×100），
  而数量用直接因子（12000 cm → 120 m）。写错不会报错，只会安静地算出一个小 4 个数量级的数字——
  所以 AC 里必须有**独立手算的预期值**（把算式写进断言注释），不要用实现去验证实现。
- **拒绝码是规格的一部分**：归一化/校验类的 AC 断言的是**具体拒绝码**（不是笼统的"被拒绝"）。
  当一个输入可能触发多条校验时，把次要缺陷（如"条目不在清单里"）推迟到对齐阶段报出，
  让首条错误指向最可行动的下一步。
- **工具截断文件**：用脚本工具写文件时，若命令未提供标准输入会把目标文件清空。
  写完 `.md` 后务必 `find . -name '*.md' -size -1k` 自查是否有意外空文件。
- **文档门是硬门**：ID 引用、预算、FR↔AC 覆盖任一失败都先修，别"稍后统一处理"。
- **别把 AC 做成人工检查**：确需人工的 AC 必须标 `manual` 并写清步骤与签署人。
- **别顺手扩大范围**：非目标清单在 `docs/design/00-overview.md` §5，开工前重读。
- **别改已 accepted 的 ADR**：要改就新写一条并标注 superseded。
- **隔离/私域类 AC 必须有"非空转"对照**：只断言"对方看不到 X"会把"把一切都删掉"的实现判为绿。
  同时断言**本侧仍能读到自己那一份**，并驱动一次**必须被拒**的载荷（把私域字段塞进出站记录）——
  否则守卫是不是活的无法区分（AC-TRUST-001 的负控）。人工门同理：三条承诺路径要"无批准即抛错"
  **且**"有批准即成功"。
- **区间/限额类 AC 先钉量纲**：授权区间是**单价**还是总额、按条目还是按包，必须写进字段名
  （`min_unit_price`）；用总额量级的区间去卡单价会让"区间内不触发门"这条断言恒假（B4 第一版即如此）。
- **AC 内改了共享配置要恢复**：测试里改完策略（如 `markup_pct`）再断言默认行为，跑在**同一个实例**上
  会把测试污染当成实现缺陷；断言前 `set_policy(原值)` 或每步新建实例。
- **同一次调用可能触发多条例外时，顺序就是契约**：承诺路径"先查批准、后查业务事实"与反过来，
  抛出的异常类型不同；AC 要钉具体异常，并在实现注释里写清顺序（首条错误最可行动）。
- **新增文档子目录是门的盲区**：`docs/work/*.md` 不匹配 `docs/work/evidence/*.md`，
  新分册要在 `12-documentation-standard.md` §1 补预算行（那是**收紧**门，不是放宽）。
  另外 `EV-<NNN>` 的定义来自**证据文件名**，索引文件不能代替 `EV-*.txt` 本体。
- **预算顶到上限时按标准顺序办**：删重复 → 删叙述 → **拆文件** → 才考虑提高预算；拆出来的分册要同时补预算行。
- **幂等去重会吃掉"重放"**：账本按 `(correlation_id, type, body_hash)` 去重，复用同一账本目录跑第二遍会得到
  **零新增事件**——"重放测试"悄悄变成"重复投递"。任何重放/确定性验证必须跑在**新账本**上
  （CLI 的 `suite` 因此每次新建并清理运行目录）。
- **派生数据不得含墙钟时间与自增序号**：要"同输入字节级一致"，`Evaluation` 这类派生结果必须**内容寻址**
  （id = 内容哈希），时间只留在账本条目上。否则 AC 的字节比对永远失败，而报错看起来像"实现不确定"。
- **先写再读**：`Ledger` 在构造时加载文件，之后由别的实例写进去的记录它看不到——采集指标/校验前
  必须**在写入之后**再构造（或用新实例读）账本，否则指标 basis 全是 0。
- **事件表是 schema**：新服务 `emit` 前必须 `bus.install_defaults()`，否则 `UnknownEventError`
  （场景/AC 驱动里最容易漏这一步）。
- **阶段推进会让某些 AC 自然失效**：若 AC 用"尚未实现的东西"做实例（如未实现的场景集返回 2），
  该任务实现后必须换一个**仍然未实现/未知**的实例来断言**同一契约**，并在提交信息里写明——
  这不是放宽 AC（断言强度不变），但要显式登记。
- **给人工的登记表必须有校验器 + 负控**：V 项（现场验证）这类人工结论如果只靠"填一张表"，
  很快会变成橡皮图章。做法：`register.json`（机器可读）+ `tools/verify.sh v` 校验
  "pass/fail 必须有 conclusion + decided_by=`human:*` + decided_at + 存在的证据文件；`open` 不得有结论"，
  并**实跑负控**（伪造结论、agent 代签、证据不存在都必须变红）。
- **人可执行的材料要"先自己走一遍"**：给供应商/采购的模板在发出去之前，用它自己的数据跑一遍
  下游链路（V-002 的表单 → 归一化 → 护栏 → 比价）。第一次跑就红了：表单单位与包的计量规则不一致——
  这种错误如果在现场才发现，整场验证白做。
- **占位式证据名要避开 ID 门的引用规则**：`EV-V0NN-<来源>.txt` 里的 `EV-V0NN` 会被文档门当成
  未解析引用（门只认 `docs/work/evidence/EV-*.txt` 文件名）。用 `EV-<编号>-V-001-<来源>-<日期>.txt`
  （角括号不构成 ID），并让校验器强制证据路径以 `docs/work/evidence/EV-<数字>-` 开头。
- **交付给人的副本不要落在门的扫描范围内**：`tools/v-kit.sh` 把执行包复制成 `.md` 会让门多扫 20+ 个文件
  （副本被计入 ID 完整性检查）；副本落成 `.txt` 即可（人读没问题，门不扫）。
- **门红就不要提交，用 `&&` 串联**：本批曾出现"先改了技能文件 → 跑门已红 → 同一条命令里继续
  `git add/commit/push`"，于是把红状态push了出去。收尾命令要写成
  `tools/verify.sh docs && git add -A && git commit ... && git push`，让门红直接短路整串动作。
- **给技能文件加内容前先看预算**：`SKILL.md` 8 KB 很容易顶到；踩坑清单溢出时按标准顺序
  **拆文件**（`references/pitfalls.md` + 在 12 §1 补预算行），而不是压缩成看不懂的短句。
- **跑门不要经管道**：`tools/verify.sh docs | tail -2 && git commit` 会拿到 **`tail` 的退出码**，
  红门被当成绿门直接提交（B7 实测：handover 1147 B 越界被提交并推送）。收尾固定写法：
  `tools/verify.sh docs > tmp/gate.out 2>&1; code=$?; [ $code -eq 0 ] && git add -A && git commit ... && git push`
  ——或先单独跑一次门看退出码，再决定提交。
- **别在中文断言串里嵌 ASCII 双引号**：`Assertion("…留下"已发送"的假象…")` 会让整个 checks 文件语法错，
  症状是 `FAIL 执行异常 — SyntaxError`（本仓已踩两次）。中文里一律用「」『』或改写措辞。
- **一次性脚本别复用变量名写不同文件**：`p = handover.md` 之后再 `p.write_text(json…)` 会把 state.json 写进
  handover.md（门立刻报预算超限）。目标文件与路径变量一一对应，换文件就换变量名。
