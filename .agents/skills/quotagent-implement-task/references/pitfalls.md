# 实现陷阱（门/流程/文档）

> 运行时侧（宿主/桥/shell）的陷阱在 [`pitfalls-runtime.md`](pitfalls-runtime.md)。

- **本页最早的一批条目已搬进归档**（单价/数量换算方向、拒绝码是规格、工具截断文件、文档门是硬门、别把 AC 做成人工检查、别顺手扩大范围、别改 accepted 的 ADR、私域类 AC 的非空转对照、区间类先钉量纲、测试污染要恢复、多例外时顺序即契约、新增文档子目录是门的盲区、预算顶到上限的标准顺序、派生数据不得含墙钟时间与自增序号）：见 [`pitfalls-archive.md`](pitfalls-archive.md)（逐字节搬出，效力不变）。
- **事件表是 schema**：新服务 `emit` 前必须 `bus.install_defaults()`，否则 `UnknownEventError`
  （场景/AC 驱动里最容易漏这一步）。
- **阶段推进会让某些 AC 自然失效**：若 AC 用"尚未实现的东西"做实例（如未实现的场景集返回 2），
  该任务实现后必须换一个**仍然未实现/未知**的实例来断言**同一契约**，并在提交信息里写明——
  这不是放宽 AC（断言强度不变），但要显式登记。
- **门红就不要提交，且跑门不要经管道**：`tools/verify.sh docs | tail -2 && git commit` 拿到的是 **`tail` 的退出码**，
  红门会被当成绿门提交（B7 实测：handover 1147 B 越界被提交并推送）。收尾固定写法：
  `tools/verify.sh docs > tmp/gate.out 2>&1; code=$?; [ $code -eq 0 ] && git add -A && git commit -m … && git push`。
- **别在中文断言串里嵌 ASCII 双引号**：`Assertion("…留下"已发送"的假象…")` 会让整个 checks 文件语法错，
  症状是 `FAIL 执行异常 — SyntaxError`（本仓已踩两次）。中文里一律用「」『』或改写措辞。
- **一次性脚本别复用变量名写不同文件**：`p = handover.md` 之后再 `p.write_text(json…)` 会把 state.json 写进
  handover.md（门立刻报预算超限）。目标文件与路径变量一一对应，换文件就换变量名。
- **改 `src/quotagent/qa/__init__.py` 的导入清单必须立刻跑 `verify.sh ac-registry`**：漏掉一个 `checks_*` 模块会**静默注销若干 AC**（本轮编辑掉 `checks_cost` → 注册表 46→44、P0 的 34 条变成 32 条），而单跑某条 AC 仍然是绿的，只有注册表级检查能发现。
- **两个摘要互相覆盖时顺序要紧**：审计包的 `pack_hash` 覆盖"除清单外的整包"、`manifest_hash` 覆盖"除自身外的清单"，而清单里含 `pack_hash` —— 必须先算 `pack_hash` 再算 `manifest_hash`，反过来会让两者互相矛盾（实测：签名的验签是过的，但 `manifest_hash` 检查失败）。
- **缺席 ≠ 未知：分类顺序就是结论**。条款比对里"单侧缺失"、"双方不一致但库不认识该键"、"双方一致"是三类不同事实：
  必须先判**双方一致（无差异）**，再判**单侧缺失**，最后才判**未知键**。顺序反过来会把"值相同但库没登记"的键
  误报成冲突（实测：护栏族级 Flag 由 6 涨到 9，看起来像护栏更"严"，实为口径错）。
- **协议别名要在消费它的服务里单点识别**：供应商报价把付款族写成 `payment_terms_offered`（交换协议既有写法），
  消费方若不认这个别名就会把整族判成"单侧缺失"。别名只在一处识别 + 写注释，调用方不许各记一遍。
- **证据与人工验证类的陷阱**（登记表校验器 + 负控、给现场的材料先自己走一遍、证据命名、交付副本落 `.txt`）见 [`pitfalls-evidence.md`](pitfalls-evidence.md)。
- **AC 夹具要先造出合法对象，再断言门禁**：给门禁类断言喂一个"根本不存在的对象"，会先撞上派生/存在性检查，看起来像实现出错（本例：`issue_po` 先判派生依据，用不存在的 award 测"缺批准"就永远测不到 `ApprovalRequired`）。正确做法：先用合法路径建出对象，再**只省掉被测的那一环**。
- **文档与代码各自声明同一组名字时，必须有双向机检**：`05-events.md` 与 `kernel/events.py` 曾出现同一事件两个名字（`confirm-requested` / `commit-requested`）与"通配声明掩盖族内改名"。运行时毫无症状，机检（名称+模式双向比对）是唯一拦截点；后续阶段的事件用「规划中」标记显式放行，而不是靠通配。
- **对文件做字符串替换必须断言命中**：一次性脚本里 `t.replace(old, new)` 在 `old` 不存在时**静默不做事**，于是"打了补丁"的错觉会留到运行期才炸（本例：给 `__init__` 加字段的锚点根本不存在 → `AttributeError` 在另一处出现）。凡替换都要 `assert old in t`。
- **改 `tools/verify.sh` 的 case 分支后必须立刻实跑该入口**：插入新分支时锚点若只取到分支标签，会把原分支的 `;;` 与函数体切开 → 整个脚本 `Syntax error`，**所有**入口都变成退出码 2（AC-RUNTIME-001/002 一类自带门的 AC 会连带变红）。插入后先 `sh -n tools/verify.sh` 再跑一次新老入口。
- **并行 subagent 的坑**（tmp 唯一命名、契约先写死、AC 不可重复注册、破坏性代码要变异自证）见 [`pitfalls-parallel-agents.md`](pitfalls-parallel-agents.md)。
- **龄期/时长必须由事实时间戳算，不得取墙钟**：`age = as_of − 事件 ts`，`as_of` 取**投影里最大的事实 `ts`**；任何「当前时间」（`Date.now()`、载荷里或配置里的 `now`）**读都不读**，并把这件事写进输出（`age_clock="facts-only"` + `ignored_now_inputs`）让它可机检。为什么：取墙钟会让同一个数字随刷新漂移 —— 两个人看同一份事实得到两个答案，"等了多久"再也无法复算与复现（本批 `gate-timeline` 的变异 1 就是把它改回 `config.now`）。
- **时间戳只到秒时，同一秒内的有序事件必须显式定序或用计数兜底**：判「还在等 / 已决」这类**终态**时，若请求与决定落在**同一秒**（实测账本的 `approval/requested` 与 `approval/granted` 同为 `21:06:37Z`），必须用「终态优先」（与账本追加序一致）或事件计数兜底，不许拿事件类型字典序当并列裁决。为什么：否则同一秒里 `requested` 会赢，页面说「待批」而 Python 侧说「已决」 —— 同一件事两种说法（对齐 `gate-timeline` 的既有判据）。
