## 0 一句话

批量人签（`quote.submit-batch` / `gate.decide-batch`）在**功能口径上一条没松**（一次署名、逐份落账、
逐份可拒、幂等零新增、50 上限具名拒、负控全拒且零新增）—— 但**在规模与并发下有一个结构性代价**：
每份草稿都是一次**同步** spawn（`app-shell.mjs` 的 `spawnSync`），N 份批量 = 事件循环被独占
`N × ~230 ms`，期间**所有人的翻页与写都在队列里等**。真手机宽度（390px）上全流程**能点完**，
登记下来的问题集中在「面板头吃掉整屏」「勾选不跨页」「导出弹层被通知盖住」三处。

## 1 规模下的批量人签（实测）

夹具：`tmp/p20-shots/seed-scale.py` + `seed-drafts.py`（真动作总线造 45 + 110 份待签草稿）。
一次调用：**40 份真草稿 + 3 份故意失败**（形状合法 `qd-supplier-<12hex>`、账本里没有）。

| 判据 | 实测 |
|---|---|
| 墙钟 | **4.27 s / 43 条（99 ms/条）** |
| 落账 | 供应商 **+120 行**（每份 `approval/requested`→`granted`→`quote/submitted`）；承包商 **+40 行**（逐份登记） |
| 逐条回执 | 43 条逐条给出 `applied|duplicates|refused` + `code` + `reason` + `next_action`；`ok=true`、`code=batch-partial`（**不是**全成/全败） |
| 故意失败 | 3 份 `draft-not-found`，**各自零新增**（`ledger_added=0`），其余 40 份不受影响 |
| 一次署名 | 40 份的 `approval/granted.comment` 全部等于本次批注（同一次署名，逐份落账） |
| 重试（原样重提） | 40 份 `already-signed`、两侧 **零新增**；3 份仍逐条具名 + 可再选 |
| 幂等（并发双击） | 同一批 5 份**同时**发两次 ⇒ 一次 `batch-submitted`、一次 `batch-already-signed`，账本只有 5 条 `quote/submitted`（5 个不同草稿，无重复） |
| 50 上限 | 51 条 ⇒ `batch-too-large`、**写者一次都没跑**、账本零新增；50 条（边界）放行 |
| 负控 | 非本人署名 403 `signer-mismatch` / `agent:*` 403 / 未登录 401 `identity-required` / 越侧 400 `cross-side-action` —— 四条合计**两侧账本零新增** |

机读读数：`tmp/p20-shots/scale-out.txt`、`p20-a-scale.json`、`p20-b-retry.json`、`p20-c-*.json`。

## 2 并发：批量人签把事件循环占满（**本轮未修，需动外壳**）

`app-shell.mjs#runPython` 用 `spawnSync`（同步）跑唯一写者 —— 单条动作几乎无感，但批量是**串行的 N 次**。

| 场景 | 期间另一个客户端的响应时间 |
|---|---|
| 无批量（基线） | 翻页 p50 **2 ms** / max 8 ms；写（`rfq.publish`）p50 76 ms |
| 50 份批量**进行中**（墙钟 11.65 s） | 翻页 **11 703 ms**、写 **11 704 ms**（各只发出 1 条，**0 条在批量期间完成**） |
| 43 份批量（4.27 s） | 与批量窗口重叠的翻页请求 **4 251 ms** |

即：**批量人签 ≈ 把整个服务冻结 `N × 230 ms`**（50 份 ≈ 11.7 s）。判据来自
`host.rows()`/`windowPanelData` 走同一条单线程路径：翻页本该 p50 2 ms。
**复现**：`python3 tmp/p20-shots/scale-concurrent.py --ids tmp/p20-shots/p20-more2-ids.json --take 50`。
**期望行为**（供外壳侧决策，本页不预设实现）：写者批处理不应独占事件循环（异步 spawn / 批量写者
一次消费多份待办件），或至少在界面上**明示"正在逐份落账 N/M"的进度**并允许其它视图继续翻页。

## 3 跨页多选：两条规则，一条是坑

| 做法 | 实测结果 | 判定 |
|---|---|---|
| 第 1 页勾 1 行 → 翻到第 2 页 → 再勾 1 行 → 点「批量人签提交」 | 实际只送出**第 2 页那 1 行**（表单上写「批量：1 行」，抓包 `ids=['qd-supplier-274e718b5f9d']`）；翻页后上一页的勾**从 DOM 消失**、计数回到 0 | **坑**（方向是"少签"，不是"错签"）：界面不提示，用户以为签了 2 份 |
| 先筛（关键字/列条件）→ 点表头的「选中全部命中行（N）」 | 命中 11 行跨 2 页 ⇒ 送出**恰好那 11 个 id**（抓包比对：`ids == 服务端 matched_keys`）；其余 77 份待签**保持待签** | **正确**：不会把没勾的签了 |
| 换筛选条件 | 「选中全部命中行」的选择**自动作废**（toast 明说），不会把上一组命中带进新筛选 | 正确 |

原始读数：`tmp/p20-shots/crosspage-out.txt`（浏览器 fetch 钩子抓到的 `ids` **逐元素**列出：
11 条 ⇔ 命中 11 行；其余 77 份批后仍待签；另含「勾 2 行只送出 1 行」那一组）。
**P20 当时的文案修**（插件 `code/ui.mjs`）：面板 note 与 `batch-too-large` 的 `next_action` 都写明
「勾选**不跨页**；要跨页按命中行签，先筛到 ≤ 50 行再点「选中全部命中行」」。
**P22 补修（同样是插件侧）**：那段话原来写在 `data.note` 里 —— 而 table 面板的 `data.note` **不渲染**
（外壳只在"没有行"时拿它当 `next_action`），用户根本看不到 ⇒ 已搬进面板 **`hint`**（会渲染），并逐字描述
界面上那两个数字（提交按钮的「已选 X 行」/「X（含跨页共 M）」、计数行的「已跨页选中 M 行」）与
「选中全部命中行（N）」那颗按钮；`batch-too-large` 的 `next_action` 同步改成"点**计数行**上那颗"。
P22 真跑（390px）：命中 30 行 / 3 页 ⇒ 点「选中全部命中行（30）」⇒ 抓包 `ids` **恰好那 30 个**、
两侧账本各 +30 条 `quote/submitted`（读数 `tmp/p22-shots/crosspage-*.{txt,json}`）。
**仍缺**（外壳侧）：手工勾选**不跨页**、翻页**不提示**；跨页选中后本页复选框不回填成勾选态
（数字是对的，只有框看不出来）—— 见 §6 D2。逐条见 `prefill-and-selection.md` §2/§3。

## 4 50 上限 × 命中数：界面反馈

390px 真机上把「我的草稿」筛成「状态=待签署」（88 行 / 9 页）→ 点「选中全部命中行（88）」→
点「批量人签提交」：表单**如实写「批量：88 行」**、确认页列出将要送出的 88 行；提交后被具名拒：

> `batch-too-large`：一次最多签 50 份，收到 88 份 · 先用「搜这块 / 按列筛选 / 状态=待签署」把命中行缩到
> ≤ 50 行（计数行会跟着变），再点表头那颗「选中全部命中行（N）」重来 —— 不要靠手工勾行：勾选**不跨页**。
> 本动作账本零新增。

**仍缺**（需动外壳）：拒了之后**没有"只签前 50 份"或"就地减选"的出口** —— 用户必须回列表、重筛、重选。
确认页也不复述条数（只在上一页写「批量：N 行」；`confirm.message` 是**静态文案**，插件侧拿不到条数）。

**做不到 / 难用清单（390px）**：

1. **面板头吃掉整屏**（最影响可用性）：一块 `table` 面板的标题 + 机制说明 + 查询条 + 列筛选 + 计数行 +
   翻页 + 「恢复默认显示」+ 镜像说明，在 390px 下**约 800px 高** —— 一屏（844px）里**看不到任何数据行**
   （见 `p20-390-19`：面板标题在 y≈144，第一行数据在 y≈880）。每换一块面板都要先滚过半屏控件。
2. **标签条重叠**：顶栏第 2 个标签的标题被「+ 新标签」压住（渲染成 `2. package FLOW-PK…新标签`）；
   窄屏下 tab 条与新建按钮**没有让位**（`p20-390-05/06/15`）。
3. **勾选不跨页**（§3）：手机上更容易踩 —— 一页只有 10–25 行，几乎必然要翻页。
4. **通知浮层盖住弹层标题**：导出预览的标题被两条 toast 压住（`p20-390-28`）；弹层已是全屏，toast 应让位。
5. **卡片里的勾选框样式**：未勾选时是一个**纯白方块**（深色主题下像缺图），与其它控件不成一套（`p20-390-11`）。
6. **命令面板**：顶栏「命令」按钮在 390px 是**单行可滑**的动作条（35 块面板 ⇒ 一屏按钮墙变成横向滚动），
   可点，但**没有分组/搜索的可见入口**；要找「批量人签提交」得横向滑很久（`p20-390-02`）。

## 7 核心流程阻断（已修：只动插件 `code/ui.mjs`）

**现象**：承包商提出授标意向后，供应商侧「发给我的授标意向」**永远是空表** ⇒ 供应商**点不到**
「确认中标」⇒ 承包商「授标承诺」被 `supplier-confirmation-required` 拒 ⇒ PO / 回签整条链**卡死**
（违反 `AGENTS.md` 规则 11「双方必须仅通过 GUI 完成全部业务流程」）。桌面与手机**同一条路**都走不通。
复现截图：`p20-390-15-award-inbox`（空）/ `p20-390-17-award-commit-result`（具名拒）。

**根因**：报价上记的 `supplier` 与供应商侧算 realm 的规则**不同源** ——
`quote-prepare/code/ui.mjs` 用 `rows0?.realm || 'supplier:gui'`（机制给的投影默认只出
`seq/type/correlation_id/actor/ts/body`，**没有行级 `realm`** ⇒ 恒取硬编码兜底），
而 `commitments/code/ui.mjs#realmOf('supplier')` 从**投递登记**读（`rfq/distributed.recipients` ⇒ `supplier:g1`）。
`award.propose` 把报价的 `supplier` 逐字抄进意向的 `delivered_to`，两侧判据不一致 ⇒ 意向投不到。

**修法**（`src/domain/quote-prepare/code/ui.mjs`）：新增 `registrationRealmOf(host)`，
取值顺序与 `commitments#realmOf('supplier')` **逐条对齐**（行级 `realm` → `po/distributed` /
`rfq/distributed` 的 `recipients[]`/`supplier`），供 `supplierRealm` 使用。两侧由此**同源**。

**修前 / 修后**（同一脚本 `tmp/p20-shots/e2e-award-po.py`，只换那一行）：

| | 草稿/报价的 supplier | 意向 `delivered_to` | 供应商「发给我的授标意向」 | 整链 |
|---|---|---|---|---|
| 修前（`e2e-before.txt`） | `supplier:gui` | `['supplier:gui']` | **空表** | 卡在 `supplier-confirmation-required` |
| 修后（`e2e-after.txt`） | `supplier:g1` | `['supplier:g1']` | **1 行** | 意向→确认→承诺→PO→回签→导出 **11/11 PASS** |
