# 路线图：mock → mvp demo → product

<!-- budget: 32 KB. 任务 ID 的真源是 progress-checklist.md，本文件只给阶段叙事、顺序与门 -->

## 0. 三条阶段规则

1. **每阶段有唯一出口门**（G0/G1/G2），门不通过不得开始下一阶段的核心工作；可并行做文档与验证。
2. **不可跳跃**：P1 不得使用"P0 没做但要手工补"的功能。若某事在 P1 必需，它就是 P0 或 P1 的任务，
   不允许"口头约定代替实现"。
3. **每阶段结束必须留下**：可复现的运行方式、AC 证据、更新后的 handover、以及本阶段承认的缺陷清单。

## 1. 总览

| | **P0 mock** | **P1 mvp demo** | **P2 product** |
|---|---|---|---|
| 目标 | 单进程端到端跑通，验证数据模型与归一化 | 双侧真实分离，跑通跨方协作与审计 | 可交付运营、可在线自进化 |
| 形态 | 1 个进程，文件账本，文件投递 | 2 个进程，relay/共享目录，CLI+队列视图 | 多租户，外部系统接入，Web 视图 |
| 关键交付 | 端到端脚本 + 确定性重放 + 指标基线 | 场景集 S1..S4 全绿 + 审计包可验证 | 自进化流水线 + 留存合规 + 运维手册 |
| 出口门 | G0 | G1 | G2 |
| 估算 | 8–12 人日 [假设] | 20–30 人日 [假设] | 30–45 人日 [假设] |
| 明确不做 | 不做 UI、不做多租户、不接外部系统、不做自进化 | 不做邮件/ERP、不做谈判、不做 canary | 不做支付/税务、不做资质征信 |

## 2. P0 mock

**目标**：用最小实现证明三件事——(a) 数据模型能表达一次真实询价往返；(b) 归一化与比价可重放；
(c) 账本能重建模型输入。**不追求可用性，追求正确性与可验证性。**

### 顺序（每步都是"能跑 + 有 AC 证据"才算完成）

| 步 | 内容 | 任务 ID | 完成标志 |
|---|---|---|---|
| S0.1 | 仓库内自包含运行时 + CLI 骨架 + 文档门工具 | T-101, T-116 | `tools/check-docs.py` 可运行且当前文档全绿 |
| S0.2 | 账本：追加、哈希链、投影重建、去重 | T-102 | 重放同输入得同结果 |
| S0.3 | 事件分发五模式 + effect/disposer 语义 | T-103 | 卸载后无残留监听器 |
| S0.4 | 插件装载与依赖协调（含依赖失活） | T-104 | 依赖下线自动失活，无脏状态 |
| S0.5 | QEP 信封 + 文件投递 + 幂等 | T-105 | 重复投递不产生第二条事实 |
| S0.6 | 归一化（单位/币种/税/计量规则）+ 拒绝语义 | T-106 | 不可归一即拒绝，无兜底 |
| S0.7 | 询价包与清单版本化 | T-107 | 已发布版本字段不可原地改 |
| S0.8 | 供应商读包、缺项、疑问草案 | T-108 | 每条抽取有 `item_id`，无引用标 `[假设]` |
| S0.9 | 成本构成（私域）+ 定价建议 + 人工门 | T-109, T-110 | 无批准记录则无法出价 |
| S0.10 | 偏差表与影响量化 | T-111 | 未标 `impact` 的偏差不进 TCO |
| S0.11 | 比价：TCO + 排序 + 引用链 | T-112 | 每个数值有引用 |
| S0.12 | 护栏：漏项 + 注入/私域检测 | T-113 | Flag 只标注，不自动否决 |
| S0.13 | 端到端脚本（S1 场景合成数据） | T-114 | 一条命令跑完 询价→澄清→2 报价→比价 |
| S0.14 | 指标基线采集（不设目标值） | T-115 | 基线报告入库 |
| S0.15 | 现场验证 V-001..V-012 | T-117 | 每条 V 有结论与来源 |

### 门 G0（由人签）

- [ ] S1 场景一条命令可重复跑出相同结果（AC-EVAL-001 的 P0 子集）
- [ ] 混合口径的 S1 场景通过归一化；被拒绝的报价有明确理由（AC-NORM-001/002）
- [ ] 无批准记录的报价无法提交（AC-APPROVE-002）
- [ ] 模型输入重建抽查 100% 一致（AC-AUDIT-002 的 P0 子集）
- [ ] `docs/work/evidence/` 中含全部 P0 AC 的真实命令输出
- [ ] V-001..V-012 全部有结论（结论可以是"证伪"，但不得留空）
- [ ] handover 与 state.json 与真实状态一致

**P0 常见失败模式（提前说明）**：把"能跑"当"跑对"（没有确定性重放）；归一化偷偷兜底；
人工门被写成可绕过的函数调用；指标基线未采集就开始设目标。

## 3. P1 mvp demo

**目标**：把单进程 mock 变成**双侧真实分离**的可用演示：两个进程、两本账本、真实跨方同步、
可导出的审计包、以及一个能演示给采购与供应商看的三场景套件。

| 步 | 内容 | 任务 ID | 完成标志 |
|---|---|---|---|
| S1.1 | 双侧进程分离 + profiles（contractor-ops / supplier-bid / relay） | T-201 | 两个 profile 各起一个**真进程**（两本账本）；`tools/verify.sh cordis` 与 AC-PLUGIN-003 均绿 |
| S1.2 | QEP 文件/HTTP 绑定 + receipt + 重发 + seq 空洞检测 | T-202 | 跨进程投递一次成功且 receipt 可查；丢包造成 `seq` 空洞时挂起并发重发请求（AC-QEP-003）；版本交集为空即拒绝（AC-QEP-004） |
| S1.3 | 三方协调 + 字段权威方 + 冲突上报与挂起 | T-203 | 非承诺字段按权威方合并；承诺字段挂起转人工；两种情况均留痕（AC-SYNC-001） |
| S1.4 | 澄清工单 + 广播完整性 + 版本变更自动重开 | T-204 | 答案广播名单缺任一在册投标人工单不得关闭；包升版后工单自动重开（AC-CLARIFY-002/003） |
| S1.5 | 包版本变更与"报价基于过期版本"标记 | T-205 | 旧版本报价被标「基于过期版本」且不进排序（AC-COMPARE-001 / AC-RFQ-002） |
| S1.6 | 护栏扩展：异常低价 / 产能冲突 / 条款冲突 | T-206, T-207 | 异常低价 / 产能冲突 / 条款冲突被标 Flag 并提请人工（AC-GUARD-001/002、AC-CAP-001） |
| S1.7 | 条款库与冲突标注 | T-211 | 条款冲突被标注并提请人工，不静默取其一（AC-TERMS-001） |
| S1.8 | 授标与 PO 闭环（意向→确认→签署→订单） | T-213 | 承诺需承包商人签 + 供应商确认；PO 只能由承诺派生（AC-AWARD-001/002） |
| S1.9 | 变更闭环（引用原单价 → 重算 → 批准） | T-212 | 变更必须引用原报价条目与单价基准；未批准的变更不影响任何金额（AC-CHANGE-001/002） |
| S1.10 | 审计包导出与独立验证 + 模型输入重建 | T-208 | 审计包可被第三方独立验证，篡改必失败；模型输入重建一致（AC-AUDIT-001/002） |
| S1.11 | 场景集 S1..S4 + 反例集（只增不减） | T-209 | s1..s4 全绿且重放 digest 一致；反例集只增不减（AC-EVAL-001/002、AC-GUARD-003） |
| S1.12 | 人工门队列视图 + 超时策略 | T-210 | 待批期间 agent 可继续其他工作；超时策略生效且**不存在自动批准**（AC-APPROVE-003） |
| S1.13 | 比较表导出（CSV/Excel） | T-214 | 导出与账本逐行一致（含 Flag 与差异说明）（AC-COMPARE-004） |
| S1.14 | 部署与操作手册（一页能跑起来） | T-215 | 一名未参与开发的工程师按手册独立部署并跑通 S1；`tools/verify.sh g1` 退出 0 |
| S1.15 | 桥接协议最小闭环（宿主 ↔ 内核） | T-216 | 桥的握手/版本协商/方法面/身份注入/错误码 AC 全绿（`verify.sh bridge`）；commit 面调用必被拒且留痕 |

### 门 G1（由人签）

- [ ] 两个进程在两台机器（或两个容器）上跑通完整链路，含一次版本变更与一次澄清广播
- [ ] 承诺类动作在**任一侧**都无法绕过人工门（对抗性测试，AC-APPROVE-002）
- [ ] 私域字段在对方视图与对方模型中均不可见（AC-TRUST-001）
- [ ] 审计包可被第三方独立验证（AC-AUDIT-001）
- [ ] S1..S4 全绿，S4 反例全部被拦且留痕（AC-GUARD-003）
- [ ] 指标有基线对比（P0 → P1），人工改写率不上升
- [ ] 一次真实供应商投递演练成功（V-011 结论为真）

### 门 G2（由人签）

- [ ] 一次自进化提案完整走完影子→门→canary→晋升，且有一次回滚被真实触发
- [ ] 内核不可被 agent patch（AC-EVOLVE-003）
- [ ] 留存与销毁策略生效且留痕（AC-AUDIT-003）
- [ ] 性能预算达标或已按结论修订预算（并记录修订依据）
- [ ] 一名未参与开发的工程师能按手册独立部署并跑通 S1

## 5. 门的签署与失败处理

- 门由**人**签（不是 agent 自评）。签署记录落 `docs/work/evidence/` 与 `progress-checklist.md`。
- 门未通过：把失败原因登记为新的反例（P1 起）或新的 V 项（P0），并把缺失任务插回 checklist；
  **不得降低门本身的要求**（降门需要 ADR 说明）。
- 每轮工作进行中，agent 必须保持 `handover.md` 与 `state.json` 与真实状态一致（`../design/07` §5）。

## 6. 风险登记册

| ID | 风险 | 影响 | 对策 |
|---|---|---|---|
| R-001 | V-002 不成立（供应商不愿结构化报价） | P1 失去前提 | P0 阶段先做盲测；若不成立，改为"人工录入 + 系统校验"路径 |
| R-002 | 归一化规则无法覆盖真实口径（行业差异大） | 拒绝率过高，流程不可用 | 规则插件化 + 按项目 patch 扩展；拒绝理由要给下一步动作 |
| R-003 | 人工门成为瓶颈 | 人力成本上升 | 队列 + 批量批准 + 阈值内自动（阈值仍由人设定） |
| R-004 | 现场数据不可得（无法采集基线） | 指标无依据 | 用合成场景先建立流程，标注 `[假设]`，P1 再校准 |
| R-005 | 双方基础设施不足（无 relay/网络不稳） | 同步不可靠 | 文件投递为最低门槛已内建（ADR-0006） |
| R-006 | 自进化引入隐性退化 | 业务风险 | ADR-0005 的五条门 + 反例集只增不减 + canary |
| R-007 | 范围蔓延（把系统做成 ERP） | 交付延期 | 非目标清单（`../design/00-overview.md` §5）在每阶段开工前重读 |
| R-008 | 单点依赖某个模型/供应商 | 成本与可用性 | LLM 适配层是接缝（Provider 可换）；离线降级为"模板 + 人工" |
