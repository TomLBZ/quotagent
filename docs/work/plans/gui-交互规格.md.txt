- 状态：**规格（未实现）**。本文件是草稿，按 D-058 用 `.md.txt` 后缀放在 `tmp/`，不进 `docs` 门扫描。

### 1.3 为什么「没有任何交互」

1. **模板里没有控件生成器**：`html(title, body, prefix)` 只拼 `<nav>`+`<h1>`+`body`；页面内容是 `handle()` 里一串 `${}` 拼接的 `<p>`/`<table>`。全文（服务器侧）只有在 admin 分支里手写的 4 个控件：提权表单、阻塞 resolve 表单、用户空间插件「装载」按钮、「提需求」表单 —— **都在 `/quotagent/admin/` 前缀下，未提权一律 401，所以三道业务/运维页面上一个按钮都没有**。
2. **"无 `<script>`"**：四道页面实测 `<script>` 计数 = **0**（也搜不到 `onclick`/内联事件）。页面是纯静态 HTML，任何交互（筛选、排序、展开、刷新）在当前架构下都不存在。
3. **"无表单以外控件"**：party 两道唯一的控件是那张**提权表单**（1 form/1 input/1 button），它属于 FR-ADMIN-002（"任意一道 UI 都提供提权入口"），不是业务交互；ops 道 **0 控件**。
4. **服务器只有 4 个写类端点**，且全在 admin 前缀：`POST /admin/api/elevate`、`POST /admin/api/blocks/<id>/resolve`、`POST /admin/api/user-plugins/(load|unload|reload|request|elevate)`；没有它们，就算把按钮画上去也无处提交。
5. **不解析查询参数**：`handle()` 只切 `url.pathname`；`url.searchParams` 全文只用过**一次**（`/admin/api/switch?to=`）。→ 筛选/排序/分页在协议层就没有入口。
6. **每道只有一条路由**：`viewMatch = /^\/([a-z]+)\/?$/` 把「视角」和「页面」绑成一一对应 → 没有下钻、没有子页面、没有分栏。
7. **一次性全量渲染**：事件表固定 `rows.slice(-40).reverse()`，无状态、无游标；想看得更细只能自己去敲 `/api/events`（页面只给了那三个 JSON 链接的文字）。

> 用户原话「看起来像一篇纯文字」的根因就是上面 1+3+7：投影层把 body 拍平成 `summary` 的 `key=value` 长串，再整段塞进表格的单个 `<td>`，既没有列、也没有折叠、也没有可点的行。

### 1.4 与需求的关系（为什么必须改）

| 需求 | 现状 | 结论 |
|---|---|---|
| `FR-UX-001` 人工门队列视图（**动作、摘要、引用链、Flag**） | 页面上只有 `approval-digest` 的**计数**（总数/时长桶/最久等待 id）；账本的**公开投影行**里只有 `seq/type/summary/ts`，**没有** `action/refs/flags/waited_seconds`，而 `approval-digest` 对缺 `waited_seconds` 的行按「整行不计入」处理 → 即使有真待批项，页面也**只可能**出计数与时长桶，四要素一个都出不来（实测当前该视角显示「共 0 项待批」= 两个 `ap-*` 都已 granted 的**真实零值**，不是因为读不到） | **未满足**。这正是「控制台不像控制台」的核心：`services/approval.py` 的 `ApprovalService.queue_view()` 在真源里已经有这四要素，但**没有任何快照把它送到 UI** |
| `FR-UX-002` / `AC-TRUST-001` 供应商看不到承包商私域 | 已满足（投影白名单 + 抑制语义），本轮**不许**动 | 回归面：新页面必须沿用 `rowsFor(view)`，不得直读原始行 |
| `FR-UX-004/005` 运维只读快照 | 已满足（`/ops/` + `/api/ops` + `pipeline.json`） | 保留 |
| `FR-ADMIN-001..010` 系统管理道 | 大体满足 | 两处**已知不一致**（见下） |
| 任务表 `T-303 Web 视图（双侧）` | 仍 `todo` | 本规格是它的落地路径 |

**已知不一致（读码判定，未实测 —— 需要真 token 才能跑）**：

1. 切道白名单两处口径不同：`webui.mjs` 用 `rules`（只有 2 个键 `contractor`/`supplier`）判 `?to=`，而 `adminGuard` 的 `views` 默认是 `['contractor','supplier','ops','admin']` → `GET /admin/api/switch?to=ops` 会回 **400 `{"error":"unknown-view"}`**，而 `FR-ADMIN-003`（"提权后可切换到**任意一道** UI"）要求它是 302。
2. `/api/status` 的 `routes` 只有 2 条，运维道/管理道/12 条 JSON 接口都不在表里 → 「路由表」这一机器可读事实与真实路由不一致。

## 2. 每个视图第一屏的设计（文字线框）

统一约定：**第一屏 = 一屏内（约 40 行 HTML）必须回答「现在有什么要我处理 / 进行中的事到哪一步 / 哪里不正常」三问**；其余区块（证据面、记分卡、价格序列、原始事件表）**下沉到子路由或折叠区**（`<details>`，无 JS）。每道页面顶部一条子导航（本道子路由 + 另三道 + 运维道）。

## 3. 交互实现方案（关键章节）

### 3.1 两个候选方案

**方案 A —— 服务端渲染 + `<form>`（选中）**

- 读交互：`<form method="get">`（筛选/排序/条数）+ `<a>`（跳转/翻页）+ `<details>/<summary>`（折叠）。全部零 JS。
- 写交互：`<form method="post" action="/quotagent/admin/...">` → 服务端处理 → **303 See Other** 回到原视图（PRG 模式），结果用一个**同形结果码**放在 `Location` 的 query 里。
- 页面模板继续用 `html(title, body, prefix)`，只扩展 `body` 的拼装（新增若干纯函数：`renderQueue()`、`renderEventsTable()`、`renderFilters()`…，放在 `host/modules/webui.mjs` 或新 `host/lib/ui-render.mjs`，均为纯函数、零 I/O）。

**方案 B —— 少量内联 `<script>` + `fetch()` 调已有路由（否决）**

- 内容：页面里给每个动作挂 `onclick`/`addEventListener`，`fetch()` 打 `/quotagent/.../api/...`，用返回的 JSON 局部改 DOM。

**为什么选 A（取舍逐条）**

| 维度 | A（SSR + form） | B（内联 script + fetch） |
|---|---|---|
| 现状可机检事实 | 保持「**0 `<script>`**」不变（可加一条门断言把它锁死） | 直接推翻该事实，且四道页面都出现脚本 |
| 可测试性 | `curl` 一行就能断言状态码/字段/表单 action（就是现有门的做法） | 需要 headless 浏览器或放弃 UI 层断言 → 门只能测 JSON 接口，测不到交互 |
| 失败同形 | 一个响应体、一套状态码即可满足「失败同形、无 oracle」 | 每个动作要两套形状（JSON + HTML 局部），两套都要维持同形 → 漂移面翻倍 |
| 与围栅门的关系 | 现有门全部照旧；新增断言挂在同一门里，断言数递增 | `t271` 的静态扫描哲学（零副作用、可枚举面）与「页面里跑代码」相冲突；还要新写 CSP/注入类断言 |
| 一致性 | admin 道**已经是** SSR+POST（提权/解阻塞/装载都是 `<form method=post>`） | 同一服务里出现两套交互范式 |
| 代价 | 每次交互一次整页刷新（本场景页面 < 10 KB，无关紧要） | 省一次刷新，但引入竞态/超时/局部失败态 |

**唯一允许的 B′（P2，可选）**：**只读**自动刷新（例如 ops 页每 30 秒重新 `fetch('/quotagent/api/obs')`）可以在**满足全部**下列条件时用一段内联脚本：① 只发 GET；② 只 `textContent` 赋值（禁止 `innerHTML`）；③ 不接触任何 token/凭据；④ 单独挂一条门断言（"内联脚本里不含 POST/innerHTML/token 字样"）。P0/P1 不做。

### 3.2 写面规则（G2/G7 的落地）

- 写类路由**只**存在于 `/quotagent/admin/**`；`/<view>/**` 只有 GET。
- 浏览器表单提交时，服务端**不新增任何写 API 调用**：
  - 解阻塞：仍写 `admin_inbox`（现有 `mkdirSync/writeFileSync/renameSync` + 0600），由 `tools/admin-apply.py` 消费；
  - 用户空间插件：仍在 `webui.mjs` 里用同一个 `userReq()` 落 `user-plugin-requests` / `user-plugin-elevations`，由 `tools/userplugin-record.py` / `tools/userplugin-elevate.py` 消费；
  - 提权：仍走 `adminGuard.elevate()`（内存会话，不落盘）。
- **实现要点**：把现有 handler 的体**抽成一个内部函数**（例如 `resolveBlock(req, res, form)`），`/admin/api/blocks/:id/resolve`（JSON 变体）与新增的表单薄壳路由**共用同一个函数** → 写调用点仍是一处，围栅门对写入的断言不需要重写。
- **P1 前不得新增落点**：承包人/供应商侧的"提交/上传"在拿到人工门决策（谁是 actor、落哪个目录、谁消费）之前一律**不做**（未决，见 §7）。

1. 请求体读取沿用现有 `readBody`（16 KB 上限）；P1 可加 `content-length > 16384` → 413 `{"error":"payload-too-large","limit":16384}`（同形，不细分）。
2. 所有新增 HTML 一律经 `html(title, body, prefix)` 输出，`content-type: text/html; charset=utf-8`、`cache-control: no-store`（沿现约定）。
3. 所有新增 JSON 一律 `JSON.stringify(payload, null, 2) + "\n"`，`application/json; charset=utf-8`（沿现约定，便于门按行断言）。
4. 新增读路由必须复用 `rowsFor(view)`（投影后的公开行）与既有插件句柄；**不得**直读 `ledgerOf(view).rows()`（会绕开投影白名单）。
5. 参数夹取一律**回显生效值**（`applied` / `data-applied`），让"夹取"这件事可被机器核对（沿用仓库既有风格：宁可夹取可核对，也不静默放行）。

## 7. 未决（不猜、不编）

1. **队列项是否允许展示 `summary`**：`ApprovalService.queue_view()` 的 `summary` 由 `_summarize(payload)` 生成，是"人可读摘要"，但本仓纪律（D-033/D-053 与 `approval-digest` 的"不出正文"）把它归在"摘要=可能带正文"。**默认做法：不出 `summary`，只出 `id/action/refs/flags/waited/policy`**；要出必须有一次人工/设计决策（并同步到快照写入器的按键白名单 + 门的新断言）。
2. **E17 静态零写面的豁免写法**：`webui.mjs` 现在**确有**两处 inbox 写入（`writeFileSync/mkdirSync/renameSync/chmodSync`）与 `new Date()`（落待处理项的时间戳）。"宿主零写面"在既有围栅门里是**逐模块**扫描（`admin-guard`/`admin-view`/`user-plugin-manager`/`plugin-market`/`storage-view`），`webui.mjs` 从未被这样扫过。要让 `webui.mjs` 也过零写面扫描，必须先决定：① 把两处写入抽到 `host/lib/`（例如 `host/lib/ui-inbox.mjs`）并给它**显式豁免**（白名单 + 注释说明"这是唯一写顶点，由 Python 侧消费"）；还是 ② 只对新增代码段做逐段扫描。**未决，需人工门**。
3. **party 道是否允许写动作**：承包商/供应商自己提交（澄清答复、凭据、材料）需要新的落点与新的 Python 消费者（现有 `admin-apply.py` 只按 `block_id` 消费 admin 提交）。在有人工门决策之前，party 道只读（本规格按此写）。
4. **`summary` 之外的 `refs` 是否需要展开成引用链**：FR-UX-001 说"引用链"，`queue_view()` 只给单元素 `refs`（`[record["ref"]]`），要真正的链条需要再回一次账本（`correlation_id`）；P1 是否做未决。
5. **门数字与 AC 表的同步**：`docs/work/acceptance-criteria.md` 里写的是历史数字（"webui 21/21"）；断言数变化后该表的文字需要人工更新（不在本轮禁改清单里的，但属于"落表规则"范畴）。**建议**：实现者在同一提交里更新这些文字，或者另开一条 AC 变更（未决）。
6. **服务重启成本**：`webui-serve.py` 启动时会先跑 `g1-walkthrough.py`（约 2–5 分钟）+ 两个 seed 脚本才监听端口；P0–P2 的每次"真机验收"都要预留这段时间（期间 `curl` 是 connection refused，**不是**代码坏了）。
