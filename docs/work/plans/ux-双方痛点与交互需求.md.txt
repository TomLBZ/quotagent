> 状态：**起草件**。本文件不改仓库任何 tracked 文件；落定（FR/AC 落表、设计文档转写、门与证据）由父方执行。
> 来源：用户 2026-09-21 原始要求（「GUI 看起来像一篇纯文字而并非一个有用的控制台，几乎没有交互能力，也没有办法实际解决用户的任何痛点，因为用户几乎什么都不能做」）+ 本文 §0.1 的实测。
> 读者：做后续实现的 agent / 人。**这是规格**：每条痛点必须追到代码或文档现状；每条交互需求必须能落成机检断言。

> 口径：优先级取 `must/should/could`（`docs/work/functional-requirements.md` §0），阶段取 `P0/P1/P2`（`docs/work/roadmap.md` §0）。本文的「P0/P1/P2」指**本批实现内的优先级**，不冒充阶段门。

## 0. 证据基线（实测，不是推测）

### 0.1 三个视图的实测形状

复现命令（本机实测，2026-09-21）：

```sh
node host/cli.mjs webui --profile webui --port 8099 \
  --ledger-contractor tmp/ui-shared/contractor/ledger.jsonl \
  --ledger-supplier  tmp/ui-shared/supplier/ledger.jsonl
```

| 路由 | HTTP | 字节 | `<button` | `<form` | `<input` | `<select` | `<script` | `onclick` |
|---|---|---|---|---|---|---|---|---|
| `/quotagent/contractor/` | 200 | 7436 | 1 | 1 | 1 | 0 | **0** | 0 |
| `/quotagent/supplier/` | 200 | 4072 | 1 | 1 | 1 | 0 | **0** | 0 |
| `/quotagent/ops/` | 200 | 2834 | **0** | 0 | 0 | 0 | **0** | 0 |
| `/quotagent/admin/`（未提权） | 401 | 24 | 0 | 0 | 0 | 0 | 0 | 0 |

（ops 字节与父方先前的 2838 差 4 B：快照刷新后一行人读摘要长度变化，非契约差异。admin 未提权 body 逐字节是固定体 `{"error":"unauthorized"}`，`AC-ADMIN-001`。）

**唯一的那 1 个 `<form>`/`<input>`/`<button>`** 是页面底部的管理员 token 提权表单（`host/modules/webui.mjs` 业务视角分支末尾），与业务无关。也就是说：**承包商采购员与供应商报价员在自己页面上的可点元素 = 0**。

页面上其余内容全是结构性不可交互的 `<table>`/`<h3>`/`<code>`：
`供应商绩效记分卡（本视角暂无可聚合的供应商行）`、`待批事项：共 0 项待批`、`谈判轮次：线程 1 / 轮次 1 / 被拒 1`、`行项目 L-001 次数 2 最低 86 中位 86 最高 86 趋势 flat`、40 行账本摘要表。

### 0.2 服务层"什么都有"，缺的是人的入口

`src/quotagent/services/` 的方法级证据（`grep -nE "^    def " 实读`）：

| 服务 | 已有方法（节选） | 人可用的入口 | 现状 |
|---|---|---|---|
| `rfq.py` | `create_package/add_items/set_interfaces/validate/publish/amend/distribute/deliveries/deadline_status/remind` | 无 | 只有 g1 走查与 qa 断言在调（`src/quotagent/g1side.py:121-179`） |
| `clarify.py` | `ask/answer/broadcast/close/on_package_rev/open_tickets` | 无 | **供应商在 GUI 里问不了问题** |
| `quotes.py` | `register/active/superseded/open_requote_requests` | 无 | **供应商在 GUI 里交不了报价** |
| `compare.py` + `export.py` | `rank/tco/recompute/cite` + `export(→CSV)` | 无 | 账本只有一行 `compare/table-exported bytes=722`；页面看不到表 |
| `approval.py` | `request/decide/queue_view/sweep/require` | 无 | 页面只有计数（`approval-digest` 插件）；`decide` 结构性不可达（§0.3） |
| `change.py` | `propose/recompute/approve/effective_total` | 无 | 页面只有一行 `delta_amount=1720`，无明细 |
| `negotiation.py` | `open_thread/declare_bounds/request_concession/submit_round/close` | 无 | 页面只有"线程 1 / 轮次 1 / 被拒 1" |
| `mail.py` | `compose/enqueue/deliver/parse/candidates/transport_status` | 无 | 运维道一句"运输通道不可用" |
| `faq.py` | `distill/publish/reuse/entries` | 无 | 页面只有条目计数 |

**结论：痛点不是"功能不存在"，痛点是"功能对人不可达"。** 这决定了 UX2 的性质——它是**可达性工程**，不是新业务能力。任何把 UX2 做成"再写一遍业务逻辑"的方案都是错的（会造出第二份口径，踩 D-056 的坑）。

### 0.3 三条硬约束（UX2 不得绕过；绕了就是设计错误）

| 约束 | 含义 | 来源 |
|---|---|---|
| **H1 宿主不写账本** | 视图层只读快照/只读账本；写入只能落"待处理项"由 Python 侧消费 | `docs/design/14-plugin-inventory.md` §2、`host/lib/ledger-view.mjs` |
| **`commit` 面永不暴露** | `approval.decide` / `quote.submit` / `award.commit` / `po.issue` / `change.approve` 只走**交互式 Python CLI**；宿主调用即拒并落 `kernel/bridge-rejected` | `docs/design/adr/0013-cordis-bridge-protocol.md` §3；`docs/work/reviews/agent-review-cordis-integration.txt:97,225`；INV-005；`AC-APPROVE-001/002`；P8 |
| **私域不出 realm** | 字段白名单由投影层强制；**管理员身份不是看到私域键的新路径** | INV-008；`AC-TRUST-001`；`AC-ADMIN-003` |

**推论（本规格最重要的一个取舍）**：GUI **永远不做"点一下就批准"**。
UX2 能做的极限是三件事——**把"要批什么"讲清楚**、**把"批完的后果"讲清楚**、**把批准命令准备好给人复制到终端**。
反之，唯一已被允许的浏览器写入路径是 admin 道的**解阻塞**（`POST /quotagent/admin/api/blocks/<id>/resolve` → `tmp/ui-shared/admin-submissions/` 待处理项 → `tools/admin-apply.py` 消费，`AC-ADMIN-005`）——它落的是 `admin/block-*`，**不是** commitment 类事实。

### 0.4 现有可达的接口面（本文"接口"列的合法取值）

实测自 `host/modules/webui.mjs` 的路由表（404 提示串亦列出全集）：

- 只读：`GET /quotagent/api/{health,status,obs,ops,pipeline,retention}`、`GET /quotagent/<view>/api/{events,history,evidence,scorecard,approvals,negotiation,faq}`
- 系统管理：`GET /quotagent/admin/{,api/session,api/blocks,api/market,api/user-plugins}`、`POST /quotagent/admin/api/{elevate,blocks/<id>/resolve,user-plugins/(load|unload|reload|request|elevate)}`、`GET /quotagent/admin/api/switch?to=<view>`
- 本文提出的**新增**接口一律显式标注「新增」。

### 0.5 一个关键缺口：写视图的入口既不存在，也不允许随便造

现在**没有任何** `/quotagent/contractor/*` 或 `/quotagent/supplier/*` 的写路径。UX2 需要它，但必须复用既有形状（`AC-ADMIN-005` 的"宿主只落 0600 待处理项 + Python 唯一写账者"），且**承诺类仍需 `human:` 批准引用**——这意味着 GUI 提交与人工签署在物理上仍是两段。这构成 §5 的头号未决项。

## 1. 双方角色画像与任务链

### 1.1 承包商采购员（角色：con-B 采购/商务，一台电脑 + 一部手机）

画像：一人身兼 3~8 个包；KPI 是"按时定标 + 不超预算 + 不被审计挑出问题"；
手上工具是 Outlook/企业微信 + Excel + 一个共享盘；对系统的耐心 ≈ 0（这是他的第二工作台，不是主工作台）。

任务链（从发起 RFQ 到定标/开票前）：

| # | 步骤 | 现在靠什么做 | 耗时点 | 易错点 | 人要想清楚什么 | 心理阻力 |
|---|---|---|---|---|---|---|
| C1 | 需求接收与采购包划分 | 图纸 PDF + 邮件 + 会议纪要；包边界写在说明里 | 半天~2 天/包 | 包边界与接口责任落不到数据里（`docs/analysis/domain-painpoints.md` §1.1） | 拆包是否值得、要不要捆绑、接口谁负责 | 怕"漏一个接口"，后期被现场和管理层两头夹 |
| C2 | 清单与计量规则编制 | Excel 工程量清单 + Word 条款 | 1~2 天/包 | 单位/税率/币种/含税口径不一致；漏项（`FR-GUARD-002` 才检测） | 计量规则写死了没有、量算错谁负责 | 怕"清单发出去才发现量算错"，会被供应商当笑话 |
| C3 | 发布 RFQ（产生不可变版本） | 定稿后发邮件；版本靠文件名 `_v3_final_真最终` | 数小时（来回盖章/审批） | 原地改已发布内容（`AC-RFQ-002` 明令禁止） | 这版能不能发、有没有遗漏条目 | 怕版本发错——**发出去就收不回** |
| C4 | 分发给投标人 + 回执 | 邮件群发 + 电话确认 | 1~3 小时 | 谁收到哪版说不清（`FR-RFQ-004` 要"谁在何时收到哪个版本"） | 该邀请哪几家、要不要补邀请 | 怕漏发导致"有人没收到"的公平性质疑 |
| C5 | 澄清答复与广播 | 邮件/电话/微信群；答案只回提问人 | **最耗时环节之一**（V-001 待验证；`domain-painpoints.md` §1.3） | 答案不广播 → 公平性风险；重复问题反复答 | 这句话该怎么写才不会让所有人重新报价 | 怕"答歪了"引发全体重报；怕被审计问"为什么只告诉他" |
| C6 | 截止管理与催报 | Excel 记日期 + 手机提醒 + 微信催 | 每天 20~40 分钟 | 临期/逾期包漏看；催了没痕迹 | 要不要延期、延期对公平性的影响 | 怕"催得晚了被怪，催早了得罪供应商" |
| C7 | 报价接收与归一 | 收 Excel/PDF，**手工抄进对比表** | 2~6 小时/包/轮 | 抄录误差 + 口径漂移（含税/单位/币种） | 这份报价的口径到底是不是我要的 | 怕抄错——**抄错就是选错供应商** |
| C8 | 比价与口径对齐 | Excel 透视表 + 自己的老模板 | 半天 | 非价格条款不量化 → "最低价中标、履约最亏" | TCO 权重怎么定 | 怕"算出来的排序和我直觉不一样，说不清理由" |
| C9 | 技术评审与偏差确认 | 逐份读正文，把偏差抄进表 | 半天~1 天 | 偏差/除外责任散落正文被忽略（`FR-DEV-001` 才捕捉） | 哪些偏差可以接受 | 怕漏掉一个致命的除外责任 |
| C10 | 授标决策与人工签署 | 会议 + 邮件确认 + 纸质签批 | 1~3 天（**等人**） | 评分表与最终决策脱节（`domain-painpoints.md` §1.5） | 选谁、为什么 | **怕签字**——签下去是不可逆的责任 |
| C11 | PO 与供应商确认 | 手工做 PO，邮件发 | 1~2 小时 | PO 与承诺不一致（`FR-AWARD-003` 要求只能由承诺派生） | 条款有没有对齐中标内容 | 怕"两边理解不一致"，将来扯皮 |
| C12 | 变更单处理 | 邮件 + 现场签证 + 事后回忆 | 每次 2 小时~2 天 | 变更链断裂、单价基准漂移（`FR-CHANGE-001` 要求引用原报价条目） | 单价基准是哪一版、差额怎么算 | 怕"供应商说是这个价，我说是那个价" |
| C13 | 结算前对账（发票核对） | 人工三方核对（订单-验收-发票） | 每单 1~4 小时 | 逐条回忆；差额找不到出处 | 差额从哪来、该不该认 | 怕认了不该认的、拒了该认的 |
| C14 | 价格谈判（让步） | 电话/面谈 + 微信 | 不定；常拖数天 | 让步无记录；越权让步（`FR-NEGO-002` 要求任何人价格让步必须人工批准） | 我的授权区间到哪、这一步让完还剩多少 | **怕越权**——让过头是自己背责任 |

### 1.2 供应商报价员（角色：sup-A 商务/预算，一台电脑，常在工地）

画像：同时跟 5~15 个 RFQ；KPI 是"中标率 + 毛利 + 不漏项不返工"；
最怕的是**白干**（投了标发现口径错/漏项/交期不可能）。

| # | 步骤 | 现在靠什么做 | 耗时点 | 易错点 | 人要想清楚什么 | 心理阻力 |
|---|---|---|---|---|---|---|
| S1 | 收包 | 邮箱/门户/微信群文件 | 分钟级但**不连续** | 收没收到、收到哪版（`quotes.py` 有 `superseded` 能力但 GUI 不可见） | 这个包要不要投 | 时间压力：**包来得又多又急，先投哪个** |
| S2 | 读包与算量确认 | 人工读图纸/清单 | **最耗时**（`domain-painpoints.md` §2 表格） | 漏项、误读规格、工时估错 | 工程量我要不要认、偏离点算不算偏差 | 怕"读漏一条，白干一个月" |
| S3 | 澄清提问 | 邮件/电话 | 1~3 天往返 | 答案只到自己手上（信息不对称） | **提问的措辞**——问得太细会暴露我的成本策略 | **怕暴露底牌**：问得越清楚，越像在报价前泄底 |
| S4 | 成本构成 | 经验 + 历史 Excel | 1~3 天 | 成本不沉淀、报价无依据（`FR-COST-001` 才条目化） | 基价取哪个、风险费留多少 | 怕"报低了接单亏，报高了直接出局"|
| S5 | 定价与授权区间 | 拍脑袋加利润 | 数小时 | 越界（`FR-PRICE-003` 有历史价格统计但**不参与决策**） | 最终数字 | **怕报价后没有回头路**（提交即承诺，`FR-PRICE-002` 要人签） |
| S6 | 交期与产能确认 | 口头问车间 + 经验 | 半天 | 产能冲突、交期不可信（`FR-CAP-001`） | 交期敢不敢承诺 | 怕"承诺了交不出来"承担违约 |
| S7 | 报价提交（承诺路径） | 邮件/门户上传 Excel | 1~2 小时 | 缺批准就提交（`AC-APPROVE-002` 会抛错） | 提交前最后一秒还想改 | **怕点错**——数字错了没法撤回 |
| S8 | 被要求降价/谈判 | 电话/微信 | 每轮 1~3 天 | 让步无记录；越限（`AC-NEGO-003`） | 让多少、底线在哪 | **怕先报价**：谁先出价谁吃亏（信息不对称） |
| S9 | 中标确认与订单 | 邮件收到中标通知 + 重填表 | 半天 | 数据重复录入（`domain-painpoints.md` §2 末行） | 合同条款确认 | 怕"中了才发现条款不对" |
| S10 | 交付与变更 | 现场签证 + 邮件 | 每次 1 天~1 周 | 变更无单价基准 | 该不该加钱、加多少 | 怕"我说加钱，承包商说你含在总价里" |
| S11 | 开票前对账 | 人工核对自己的报价/变更/验收 | 每单 2~4 小时 | 与承包商口径不一致 | 差额依据 | 怕"对不上账又要等三个月" |

### 1.3 两链的交接点（摩擦集中在这里）

| 交接点 | 承包商看到什么 | 供应商看到什么 | 现在靠什么 | 摩擦性质 |
|---|---|---|---|---|
| J1 包发布/分发 | 一个包 + 邀请名单 | 一份 Excel/PDF 邮件 | 邮件 | 口径与版本 |

| J3 升版 | `deltas` 字段级差异 | 一句"清单更新了" | 邮件 | 版本错配（会直接导致作废报价） |
| J4 报价提交 | 一份 Excel | 自己发的邮件 | 邮件 | 抄录误差 |

| J7 变更 | 签证单 | 签证单 | 邮件/现场 | **扯皮高发区** |
| J8 对账 | 订单-验收-发票 | 报价-变更-验收 | Excel | 口径不一致 |

## 2. 痛点清单（带证据）

编号 `P-01..P-22`。标 **[人类痛点]** 的是**人的阻力/时间压力/信任/信息不对称**问题（不是技术问题），共 **9 条**（P-03/04/06/07/12/13/14/18/20）。
每条格式：`痛点 → 后果 → 现在为什么解决不了（代码/文档现状） → 期望的产品行为 → 优先级`。

| ID | 痛点 | 后果 | 现在为什么解决不了（代码/文档现状） | 期望的产品行为 | 优先级 |
|---|---|---|---|---|---|

## 3. 交互需求（可落合同）：FR 草案 + AC 草案

编号 `FR-UX2-001..020`（**草案·未落表**），每条至少一条 `AC-UX2-00x`（**草案·未落表**）。
AC 写法遵循本仓纪律：**可执行命令 + 明确断言 + 变红反例**；不允许"人工检查一下"（`acceptance-criteria.md` §0）。
所有 AC 一律要求：**不许出现第二份口径**（数字必须来自既有服务/快照，宿主不得自算，D-055/D-056）、**不许"看起来健康的零"**（降级必须 `degraded`+`reason`+`next_action`）、**私域与正文一律不出现**（INV-008）。
落表前提：按 D-059，FR 行与 AC 行**同批**进 `docs/work/functional-requirements.md` / `docs/work/acceptance-criteria.md`，且 AC 的"命令"指向的**门与证据必须已真实存在**。

### 3.5 与既有需求的关系（不许重复造）

- **复用**（不得另写一份）：`ApprovalService.queue_view`（四要素）、`RealmProjector.project`（字段白名单）、`ExportService.to_csv`、`sourcing` 插件的 `coverage/gaps/expiring`、`pipelineView.snapshot`、`adminGuard` 的提权与统一拒绝体、`tools/admin-apply.py` 的"待处理项 → 唯一写账者"形状。
- **一致性纪律**：同一数字在页面与其他读取面（快照、`api/*`）必须同源同值（D-055/D-056）；要新口径就**新增键**，不许改现有键的语义。

## 4. GUI 可行动作清单

每个视图：**第一屏必须看到的 3 件事（新用户三步上手）** + 动作表（控件 / 接口 / 失败时人看到什么）。
"接口"列取值见 §0.4；标「新增」的是本规格提出的新端点，需随实现同批登记。
**通用失败规则**（适用于下表每一行）：任何失败都必须在**动作发生的原位**给出三行——人话 / 原始 `code` / `next_action`（FR-UX2-008）；未接线的动作一律 `disabled` + `data-reason`（FR-UX2-020）。

## 5. 明确不做 与 未决

### 5.1 明确不做（6 条）

1. **不做"浏览器点一下就批准承诺"**。`approval.decide` / `quote.submit` / `award.commit` / `po.issue` / `change.approve` 永远不经浏览器（ADR-0013 §3、INV-005、`AC-APPROVE-001/002`、P8）。任何为了让 UX "更好用"而放宽这条的提案都应被直接拒——它是**结构性事实**，不是实现细节。
2. **不做新的业务判定**。视图层不得重算覆盖率、TCO、轮次、额度、待批数（D-055/D-056 的教训）。所有数字必须来自既有服务回放或 Python 侧快照；宿主侧只许渲染、截断（并报被丢条数）、降级。
3. **不做主动外发通知**（邮件/短信/IM）。`mail.py` 的传输边界在无凭据时必须返回 `unavailable`（`AC-MAIL-001`）；UX2 不接 SMTP、不引第三方、不发提醒。要提醒请外部轮询 `api/today`。
4. **不做前端框架与第三方依赖**。宿主侧白名单纪律（node 内建 / `cordis` / `lib/std-schema.mjs`）同精神延伸到浏览器侧：原生 HTML + 渐进增强；**JS 不可用时页面必须完整可读可操作**（核心动作走 `<form>`）。
5. **不做供应商侧对承包商私域的任何间接暴露**（`INV-008`/`AC-TRUST-001`）。包括"用排名暗示标底""用 Flag 阈值暗示成本线"这类间接泄露——`FR-UX2-012` 的 AC 已把这类反例写成断言。
6. **不做管理员身份的数据特权**。提权只打开"面板可见性 + 跨道导航 + （admin 专属的）解阻塞提交"；字段白名单一字不改（`AC-ADMIN-003`）。

### 5.2 未决（5 条，需用户/后续决策）

1. **GUI 提交与人工签署的两段式体验**（头号未决）。按现行约束，GUI 提交只能落待处理项，而承诺类消费**仍需 `human:` 批准引用**——于是"填表 → 去终端批准"是必然的两段。三种候选：① **复制命令交接**（本规格默认，零新安全面）；② **本地终端助手**（GUI 给一条本地命令，人在自己机器执行）；③ **per-approval 本机口令**（人在 GUI 输入一次性口令，Python 侧验证——**需要新的信任模型与 ADR**，不得由 agent 自定）。
2. **待处理项目录的隔离与清理**：`AC-ADMIN-005` 用了 `tmp/ui-shared/admin-submissions/`；业务侧若要复用同一形状，目录命名、0600 归属、消费后归档（`applied/`）、**崩溃后残留件如何处置**需定口径（避免"看起来提交了其实没消费"）。
3. **草稿的存储位置与跨设备**：`FR-UX2-004` 暂定宿主侧文件 + 本地缓存。若供应商要在手机与电脑间续写，需引入账号/设备标识——这触及身份模型，本规格**不擅自决定**。
4. **首屏"三件事"的排序权重**：是否按"临期优先 / 金额优先 / 最久未处理优先"？权重属公司策略，建议落 patch（人类可写），不由 agent 定默认值。
5. **`FR-UX2-020` 的"未接线"判定粒度**：是"路由存在即算接线"还是"路由 + 快照字段齐才算"？前者简单但会放过"路由在、数据永空"的假可用；建议取后者，但需父方裁决并写进门。

### 5.3 落表与实现顺序（给父方）

| 步 | 动作 | 完成判据 |
|---|---|---|
| 1 | 先写门（`tools/verify.sh ui-actions`）与反例，再改渲染（RED → GREEN） | 门在旧页面上**必须真变红**（现在是 0 script / 0 元素，天然红） |
| 2 | Python 侧补只读端点与快照字段（`api/today`、`api/packages`、条目化 `api/approvals`） | 新键只增不改（D-056）；快照仍不含正文与私域 |
