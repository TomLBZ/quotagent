# 07 自实现与在线自进化

<!-- budget: 24 KB. 本文件定义 agent 能改什么、以什么流程改、失败如何回滚 -->

## 1. 设计目标与红线

**目标**：让 agent 能在不做人类介入的情况下改进系统的**外围**——提示词、策略参数、解析规则、
新增能力插件——并保证每一次改进都可测量、可回退、可追责。

**红线（P1 / ADR-0002）**

| 不可自改 | 原因 |
|---|---|
| `kernel/*` 命名空间（账本、事件分发、插件装载、QEP 信封校验） | 内核是信任根；自改内核使一切证据链失效 |
| 账本事件类型的语义与字段含义 | 审计要求（P4）；改语义即改历史 |
| QEP 协议版本与信封字段 | 跨方契约，单方改动会静默破坏对方（P7） |
| 人工门的存在性与批准要求 | 承诺治理是人的权力，不是可优化目标 |
| 密钥与信任配置 | 安全边界 |

## 2. 可写面清单（agent 的自改范围）

| 可写面 | 形式 | 审批 | 回滚方式 |
|---|---|---|---|
| 提示词片段（角色、思路、示例） | `prompts/*.md` 片段，按插件条目挂载 | 影子+门自动；涉及硬约束文本需人审 | 卸载该条目（effect 回收） |
| 策略参数（TCO 权重、护栏阈值、让步上限） | 组织/项目级 patch | **人设定基线，agent 只能在区间内提案** | 恢复上一版 patch |
| 归一化规则（单位换算、计量规则映射） | `norm` 的规则插件 | 门通过即可 | 卸载规则条目 |
| 异常检测规则（guard 规则） | `guard.register_rule()` | 门通过；阈值变更需人批 | disposer |
| 新能力插件（如新的成本因子模型） | 新 Provider 实现 | **人工批准** | 卸载 fiber |
| 评测用例（新增反例集） | `eval` 套件条目 | 门通过即可 | 删除条目 |

**注意**：策略参数与护栏阈值属于"安全相关"，agent 只能提案、不能落定；这条界限写在
`AGENTS.md` 与 `ctx.evolve` 的不变量里，并由 INV-010 检查。

## 3. 流水线（六步）

```
1 观察    observe(window)   → 从账本与评测报告提取信号：
                             护栏触发率、人工改写率、澄清轮次、比价耗时、被拒输出比例、
                             影子重放差异、人工否决的提案类型
2 提案    propose(signal)   → 产出 Proposal{ id, target(可写面), diff, rationale,
                             expected_effect{metric, direction, magnitude},
                             risks[], rollback_plan, evidence_refs[] }
3 影子    shadow(proposal)  → 在 evaluator profile 上对历史账本重放，
                             用同一批历史输入跑改动前后两套逻辑，输出 MetricDelta
4 门      gate(report)      → 门槛（默认，可由人调整）：
                             - 目标指标不退化（>= 基线）
                             - 所有不变量测试通过（INV-001..010）
                             - 反例集（red-team）全部通过
                             - 成本/延迟不超预算（见 10）
                             - 无新增人工门（不允许"多问人"来换取正确率）
5 canary  promote(scope)    → 先在单标段/单供应商/单一报价类型上生效
6 晋升/回滚 promote|rollback → 观察窗口内指标达标 → 全量生效；
                             越界即自动回滚（卸载 patch，effect 回收）
```

**每一步都产出一条 `evolve/*` 账本事件**，因此"系统是怎么变成现在这样的"永远可回答。

## 4. 奖励作弊与自我欺骗的防护

自进化最大的风险是优化了指标却破坏了业务。对策（逐条对应可机检手段）：

| 风险 | 对策 |
|---|---|
| 指标被优化而非业务被改善 | 指标必须来自账本事实（人工改写率、澄清轮次），不接受模型自评 |
| 用"多问人"换正确率 | 门里显式约束"人工介入率不上升" |
| 削弱护栏 | 护栏规则与其阈值不在 agent 可落定范围；反例集包含历史护栏触发样本 |
| 改动使重放不再确定 | 确定性检查（同输入同输出）作为硬门 |
| 提案例被反复重试直到通过 | 提案需附过去 N 次相似提案的结果；第三次同类失败必须转人 |
| 通过修改评测用例提高通过率 | 评测用例改动必须且只能追加，且旧用例永不删除；新增用例需人批 |

## 5. 崩溃、压缩与接手的无缝性（本仓库的工程保障）

系统级（运行时）：
1. 账本是唯一权威（`03` §7）；任何进程崩溃后从账本重放恢复。
2. 每个注册都是 effect（P3）：崩溃遗留的订阅/定时器在重启时不复活；残留状态由
   `ctx.plugin` 的装载阶段重新建立，且建立过程幂等。
3. 未落账的内存草稿视为可丢失（Intent 层），不做"半个报价"的恢复。

开发级（本仓库）：
4. `docs/work/handover.md`（≤1024 B）：当前阶段、最后验证命令与结果、**下一步唯一动作**、阻塞。
5. `.agents/state.json`（机器可读）：`phase / next_task / last_verified / blockers / open_questions`。
6. `docs/work/progress-checklist.md`：任务级状态（`todo|doing|blocked|done`）+ 证据链接。
7. `.agents/sessions/`：每轮一行（轮次、做了什么、验证结果、下一步），给下一次接手当索引用。
8. **恢复顺序固定**：`handover.md` → `state.json` → `progress-checklist.md` → 动手。
   这三份文件互相冗余，任一缺失仍可恢复——这是对"上下文压缩吃掉细节"的对策。

## 6. 人的介入点（不可被自动化移除）

1. 设定指标基线（P0 采集）与门槛值。
2. 批准策略参数落定与安全相关阈值变更。
3. 批准所有对外承诺（报价、授标、PO、变更）。
4. 裁决承诺字段的跨方冲突（`03` §4.4）。
5. 内核变更与协议版本升级（必须走 ADR）。

## 7. 与 Cordis 的对应关系

| 本设计 | Cordis 机制（`../analysis/cordis-architecture.md`） |
|---|---|
| 卸载即回滚 | `fiber.ts:277-340` effect/disposer 逆序回收 |
| 改配置先过否决点 | `fiber.ts:478-495` `internal/update` waterfall |
| 依赖变化自动收敛 | `fiber.ts:385-415` epoch 比较 |
| 在线替换不重启 | `packages/hmr` |
| 改动归属与冲突上报 | `include/journal.ts:195-242` `reconcile` |

**我们多加的一层**是"评测门 + canary + 自动回滚"——Cordis 保证"能安全地换"，
我们还要保证"换得对"。
