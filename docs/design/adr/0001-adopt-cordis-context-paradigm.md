# ADR-0001 采用 Cordis 的 context 范式作为系统设计内核

Status: accepted

## Problem

我们需要一个能让 agent 长期在线实现与改进的运行时形态。现实约束是：系统会在多年内被反复
改动（新增行业规则、换供应商、加参与方），而采购场景要求**可审计、可回退、不可悄悄改历史**。
若采用"中心服务端 + 大框架 + 业务代码铺开"的常规形态，改动的影响半径不可估计，
agent 每次改动的风险都会压在人类审核上，自进化将无法成立。

## Decision

采用 Cordis 的三条设计纪律作为本系统的架构内核，**借鉴设计而不引入其代码**：

1. **副作用可回退**：任何注册（订阅、定时器、外部通知、缓存）都必须交出 disposer，
   卸载时逆序回收（对应 `packages/core/src/fiber.ts:277-340`）。
2. **依赖声明式协调**：能力声明它需要什么，运行时按依赖就绪情况激活/失活，
   不做启动顺序编排（对应 `fiber.ts:385-415` 的 epoch 机制）。
3. **组成即数据**：系统的装配以分层的、可编辑的配置条目表达，运行时改动有明确归属与冲突上报
   （对应 `loader` + `include` 的 patch/journal）。

对应到本系统：内核四件事（账本、事件分发、插件装载、QEP 信封校验），其余一切为插件。

## Consequences

**正向**

- 改动的爆炸半径按插件边界被限制；"卸载一个能力不留残留"成为可机检不变量（INV-002）。
- 组成改变不需要重启，也不需要人工编排启动顺序，为在线自进化提供前提。
- 配置分层（行业模板→公司策略→项目→标段）天然对应采购组织的授权层级。

**负向**

- 需要自建内核（不 vendor），初期成本高于拼装现成框架。
- 开发者必须理解 effect/coeffect 的语义；不理解就会写出"看起来能跑但不能卸载"的插件。
- 内核能力刻意保持弱，行业逻辑必须全部在外围实现，前期需要更多脚手架。

## Alternatives rejected

| 方案 | 否决理由 |
|---|---|
| 直接 vendor Cordis 源码 | 其 API 自述未稳定（`README.md`）；它只覆盖单进程组合，跨方账本与承诺治理仍需自建，徒增跟随成本 |
| 常规微服务 + 数据库 + 迁移脚本 | "改动影响半径"靠约定控制，无法机检；卸载/回滚没有结构性保证 |
| 事件溯源框架（现成 ES 库） | 能解决账本，但解决不了"能力可热插拔 + 依赖响应式协调"这一层，而后者是自进化的前提 |
| 工作流引擎（BPMN 类） | 流程可配置，但副作用与依赖仍由外部代码承担，回退语义缺失 |

## Revisit conditions

1. Cordis 发布稳定版且其 loader/include 语义被正式文档固定后，可重新评估 vendor 的收益。
2. 若实测发现自建内核在性能上不可接受（`docs/design/10-nonfunctional.md` §3 预算无法达标），
   重新评估内核边界划分（例如把账本换成嵌入式数据库）。
3. 若现场验证（V-007）表明协作实为同一法人内部的中心化平台，本条前提消失，
   应改用中心权威模型。
