# ADR-0014 P1 的推进前提（V 假设通过）、MVP 判据与削减顺序

Status: accepted

## Problem

P0 的最后一步（T-117 现场验证 V-001..V-012）需要真实承包商/供应商参与，结论只能由人签。
用户指令（2026-09-12）：**假设所有这些人工辅助验证都通过，全面推进直到完成 MVP**；
人工批准原则上默认通过；**独立 agent 的讨论结果可以代替人类决策**，只要留下明确的决策记录。

需要定死：(1) "假设通过"在仓库里怎么表达，才不会变成**伪造结论**；(2) MVP 到底以什么为完成判据；
(3) 时间不够时先砍什么、以及**绝不许假**的清单；(4) agent 代替人决策的边界与留痕方式。

## Decision

1. **假设的表达方式**：`docs/work/validation/register.json` 的 12 条保持 `status:"open"`（不变），
   另加顶层 `planning_assumptions[]`，逐条写明"按用户 2026-09-12 指令，P1 开发以该 V 通过为前提"，
   并标 `not_a_conclusion: true`。**任何情况下都不得**把假设写成 `status:"pass"`、
   不得填写 `conclusion`/`decided_by`；T-117 的 `done` 与 G0/G1 签署仍需人工
   （`tools/verify.sh v` 会拒绝越权登记）。
2. **agent 代替人决策的边界**：可以——架构/协议/批次顺序/范围削减/技术取舍（记录到
   `docs/work/decisions.md` + 评审原文 `docs/work/reviews/` + 架构级写 ADR）。
   不可以——V 项结论、G0/G1 签署、承诺类动作的批准（`07` §6 的"不可移除的人的门"）。
3. **MVP 完成判据（P1 的 Definition of Done）**：两个真人、两台机器上两个**真进程** + 共享目录，
   走完一轮：`发布 → 澄清广播 → 升版 → 报价 → 比价与 Flag → 授标 → 变更 → 审计包独立验证`；
   且同时满足：
   - 任一承诺动作**在任一侧都无法绕过人工门**（对抗性测试，AC-APPROVE-002 的跨进程版）；
   - 私域字段在对方的**投影 / 模型输入 / 视图**三处均不可见（含非空转负控，AC-TRUST-001）；
   - 全程**可离线重放**且第三方可**独立验证**审计包（篡改必失败，AC-AUDIT-001）；
   - S1..S4 场景全绿、S4 反例全部被拦且留痕（AC-GUARD-003）；
   - 无 Node 环境时 P0 的 34 条 AC 与文档门仍全绿（可复跑性不退化）。
   演示形态：**命令行、30–40 分钟**，观众 = 采购负责人 + 供应商。
4. **削减顺序（自上而下，砍完仍能演完上述剧幕）**：C1 HTTP relay（退回共享目录）→
   C2 宿主视图/中间件（只留装配 + profiles + 配置否决 + 桥接）→ C3 条款库缩到付款/质保/罚则三条 →
   C4 导出只做 CSV（不做 xlsx）→ C5 产能只留"`firm` 交期不可变 + 简单日历冲突" →
   C6 超时提醒自动化 → C7 队列只做只读快照 → C8 S2/S3 缩到 20 条目。
5. **绝不许假（8 项）**：人工批准记录（无代签/无自动批准/无旁路）· 私域三处过滤与负控 ·
   账本哈希链与审计包独立验证 · 归一化拒绝不兜底 · 重放确定性（必须在新账本上跑）·
   `seq` 空洞不跳号 · 反例集只增不减 · 两个真进程（不得用同进程两对象冒充）。
   另外：V 项与 G0/G1 只能人签；证据必须是原始命令输出（`docs/work/evidence/EV-*`）。
6. **执行顺序**取评审 B 的 16 批依赖序（`docs/work/decisions.md` D-007）：
   B1 文档缺口 → B2 双侧进程分离 → B3 桥最小闭环 → B4 QEP 跨进程绑定 → B5 三方协调 →
   B6 澄清工单 → B7 版本与过期标记 → B8/B9 护栏与条款 → B10 授标与 PO → B11 变更闭环 →
   B12 队列视图 → B13 审计包 → B14 比较表导出 → B15 场景集 → B16 手册与 `g1`。
   **写冲突面同一时刻只允许一批持有**（`kernel/qep.py`、`services/rfq.py`、`tools/verify.sh`、
   12 §1、`progress-checklist.md`、`handover.md`、`state.json`、`evidence/INDEX.md`）。
7. **P1 的模块演进交付（评审 C 的 8 条最小集，按可验收语句）**：每个模块有 manifest
   （`name/inject/Config/apply`）+ fixture 断言 + ≥1 个 repo AC 形状的契约测试；
   H1/H2/H3/H5/H6 五条宿主强制不变量各带一个**会变红的负控**，入口 `tools/verify.sh invariants`；
   演进门骨架（提案记录、patch/journal 归属、隔离 realm 影子挂载、按 dispose 回滚、
   晋升需人工 `approval_ref`）。canary 路由与自动晋升留 P2。

## Consequences

**正向**

- 不被现场验证阻塞：P1 可以连续推进，同时把"假设"与"结论"在数据层分清，不会污染证据链。
- MVP 判据可演示、可机检（每条都映射到既有或已排期的 AC），削减顺序让"时间不够"变成有预案的取舍。
- agent 代替人决策有边界与留痕：速度有了，审计面没丢（决策日志 + 评审原文 + ADR 三层）。
- "绝不许假"清单把最容易走捷径的地方（批准、私域、证据、确定性）提前钉死。

**负向**

- 若真实 V 结论与假设相反（尤其 V-002 供应商不愿提交结构化报价），受影响功能要重新定范围——
  这意味着 P1 的部分成果可能被砍（本 ADR 明确接受这个风险，且要求记录为新决策行）。
- `planning_assumptions` 是一个新的数据形态，需要校验器与文档同步维护（否则会退化成口头约定）。
- 16 批串行关键路径较长；并行度受"写冲突面单批持有"限制。

## Alternatives rejected

| 方案 | 否决理由 |
|---|---|
| 等 V 项全部有真实结论再开 P1 | 与用户指令冲突；且现场验证周期不可控，会让项目停滞 |
| 直接把 V 项标 `pass` 以便"流程顺畅" | 伪造结论，违反规则 6 与"证据可执行"；校验器已会拒绝 |
| 不设削减顺序，到时临场决定 | 现场决策质量最差；且容易砍到"绝不许假"的项 |
| 让 agent 也代签 G0/G1 与人批准 | 直接摧毁 `07` §6 的人的门与 INV-005；承诺类动作从此不可信 |
| 只做单进程"两个对象互相调用"来冒充双侧分离 | 与 S1.1/门 G1 的判据冲突；无法证明真实跨方语义 |

## Revisit conditions

1. 任一 V 项拿到**真实结论**且与假设相反 → 立即冻结对应批次，写新决策行与新 ADR，重定范围。
2. V-002 若被证伪（供应商不接受结构化报价）→ P1 的目标从"结构化报价闭环"退回"在既有流程里插一层一致性"
   （`11` §3），MVP 判据随之改写。
3. 削减顺序若被动用到 C3 以下 → 需重新评估"MVP 是否还满足门 G1"，并由人签确认范围缩小。
4. 自进化流水线（`07` §3）在 P2 上线后，第 7 条的演进门骨架换成实际 loader/journal 机制，届时追加一节。
