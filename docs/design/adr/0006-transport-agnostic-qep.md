# ADR-0006 QEP 传输无关，协议版本不兼容即拒绝

Status: accepted

## Problem

双方的基础设施天然不对等：一方可能有门户与 API，另一方只有邮件和企业微信。若协议绑定
某一种传输（HTTP 服务、消息中间件），则最小可用的接入方被基础设施门槛挡住，
项目一启动就要先做集成工程，而不是先验证业务闭环。

同时，跨组织协议必须能长期演进。若允许"对方版本较低就静默降级处理"，会出现
语义被悄悄丢弃（例如批准链字段被忽略），而这类丢失在审计时才发现。

## Decision

1. **信封自包含**：`qep_version / msg_id / correlation_id / seq / prev_hash / sender /
   refs / type / class / body_hash / body / approvals / signature`（`03` §2）。
   任何承载方式只要能把这段 JSON 完整送达即可成立。
2. **三种绑定同语义**：共享目录（P0）· HTTP relay（P1）· 邮件附件（P2）。
   绑定只影响投递可靠性，不影响语义；relay 不解析 body。
3. **明确拒绝语义不兼容**：`qep_versions` 交集为空 → 拒绝通信并产出 `kernel/qep-rejected`（含双方版本列表）。
4. **特性级降级必须留痕**：`features` 不匹配时退到双方都支持的最小子集，并落账本事件；
   只允许降级"可选特性"，**不允许降级**批准链、版本绑定、签名校验这三项。
5. **幂等**：`msg_id` 去重 + `(correlation_id, type, body_hash)` 视为同一事实；
   重发保持 `msg_id` 与内容不变。

## Consequences

**正向**

- P0 可用共享目录跑通全链路，零基础设施依赖（与 `11-integration-map.md` 的降级规则一致）。
- 升级路径可控：双方可独立升级，过渡期内新旧报文并存。
- 不兼容时失败显式、可诊断（对端版本列表在事件里）。

**负向**

- 文件/邮件绑定缺乏投递保证，需要显式重发与 receipt 机制，工程复杂度高于"直接调 API"。
- 自包含信封体积较大（报价体量大时需要分片策略，P1 补充）。
- 同一事实可能以不同 `sent_at` 多次到达，去重逻辑必须严谨。

## Alternatives rejected

| 方案 | 否决理由 |
|---|---|
| 只支持 HTTP + OAuth 的"标准"API | 把集成门槛前置，违反"最小可用先跑通" |
| 绑定消息队列（Kafka/AMQP） | 双方都要改基础设施，项目初期不可行 |
| 用 Excel 交换（沿用现状） | 无签名、无版本、无幂等，等于不做协议 |
| 版本低即降级处理 | 语义可能被静默丢弃，与 P7 冲突 |

## Revisit conditions

1. 若双方均具备成熟网关，且共享目录/邮件绑定在实践中出现不可接受的丢件率，
   可把 HTTP 定为默认绑定（语义不变，仅默认值变化）。
2. 若报价体量普遍超过单封邮件/单文件上限，需要新增分片与断点续传特性（走特性级留痕路径）。
