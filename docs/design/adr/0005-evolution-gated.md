# ADR-0005 自进化必须经影子重放 + 评测门 + canary

Status: accepted

## Problem

"在线自进化"若直接在生产上生效，等价于把未经检验的改动推给正在进行的商业谈判。
采购场景中一次错误排序或一次错误护栏阈值，可能直接造成选错供应商或漏检异常低价，
而其后果在数周后的履约阶段才暴露。

## Decision

任何自进化改动必须走六步（`07` §3）：观察 → 提案 → 影子重放 → 评测门 → canary →
晋升/回滚。门槛默认包含五条**同时**满足：

1. 目标指标相对基线不退化；
2. 全部不变量（INV-001..010）通过；
3. 反例集（red-team）全部通过，且用例只增不减；
4. 成本与延迟不超预算（`10` §3）；
5. **人工介入率不上升**（禁止用"多问人"换正确率）。

配套：

- 每个提案必须自带 `rollback_plan`，且回滚以卸载 effect 实现（不依赖人工删文件）。
- 每次晋升与回滚都落 `evolve/*` 账本事件，`../work/progress-checklist.md` 记录提案 ID。
- 安全相关参数（护栏阈值、策略权重）agent 只能提案，落定由人批（ADR-0002 开放面）。

## Consequences

**正向**

- 改动上线前有历史数据的经验证据，而不是靠"看起来更聪明"。
- 回滚是结构性能力（卸载），不依赖人记得怎么改回去。
- 反例集累积使系统对已知陷阱单调变强。

**负向**

- 迭代变慢（每轮需影子重放与评测），早期收益兑现慢。
- 需要历史账本与场景集作为燃料；P0/P1 期间数据不足，自进化只能在 P2 真正启用。
- 门槛本身可能被误设（过松漏检、过严无进展），需要人定期校准。

## Alternatives rejected

| 方案 | 否决理由 |
|---|---|
| 直接在线生效 + 监控回滚 | 商业决策的损失不可由"回滚"挽回（已经动了对手方） |
| A/B 实验（生产分流） | 无法对同一包做两次授标；场景不满足可对照条件 |
| 只做离线评测，不做 canary | 离线场景集无法覆盖真实数据分布漂移 |
| 让人审每个提案 | 回到人工瓶颈；且人无法评审大模型提示词的细节差异 |

## Revisit conditions

1. 当反例集与场景集覆盖足够、且历史事故率低于阈值时，可缩短 canary 观察窗口。
2. 若引入形式化性质检查（不变量可机械证明），可减少影子重放的必要性。
