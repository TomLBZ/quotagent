# Cordis 可发扬的设计优势（以及为什么它们对我们的领域不是装饰）

<!-- budget: 20 KB. 前件证据见 cordis-architecture.md -->

本文把 Cordis 的设计优势逐条拆成"机制 → 为什么强 → 在本领域（承包商↔供应商采购报价）
怎么用 → 迁移风险"。最后给一张概念映射表。

## 优势 1：副作用是一等公民，且天生可回退（revertible effects）

- **机制**（`代码` `packages/core/src/fiber.ts:277-340`）：注册即交出 disposer；卸载时逆序执行；
  生成器可边产出边注册；重复释放 no-op；已卸载 fiber 再注册直接报错。
- **为什么强**：它把"清理"从纪律变成类型化的运行时契约。插件生态能长到几千个而不烂尾，
  靠的就是这条：**没人能靠"忘记 unsubscribe"制造隐性状态。**
- **本领域怎么用**：报价 agent 的每一次动作都伴随外部副作用——发澄清函、写账本、占用一个报价
  截止窗、给供应商发提醒、把标底写进内部评分。任何一次"改主意"（撤回授标意向、撤销一轮谈判、
  回滚一次误发的 RFQ 修订）在系统里应当是**卸载 = 全部副作用回收**，而不是靠人去追邮件。
- **迁移风险**：**外部世界不可回退**。已发出的邮件、已提交给对手方的报价版本无法撤回。
  因此本系统区分两类 effect：`local-effect`（本地状态、缓存、订阅、定时器 —— 必须可回退）
  与 `commitment-effect`（对外承诺 —— 不可回退，改为"可撤销的意向 + 追加式更正条目"，见 ADR-0004）。

## 优势 2：依赖声明 + 响应式协调（reactive coeffects）

- **机制**（`代码` `fiber.ts:385-415` 的 epoch 比较 + `reflect.ts:207-229` 的 notify 反向扫描）：
  插件写下它依赖哪些服务，运行时把依赖状态编成 epoch；依赖上下线自动触发激活/失活。
- **为什么强**：**没有启动顺序编排，也没用"我等一下再试"的重试循环。** 系统组成改变时，
  受影响的部分自己收敛到正确状态。
- **本领域怎么用**：一条报价链路本身就是依赖图——"提交报价"需要：RFQ 当前版本已冻结、
  规范库已对齐全、汇率已取到、供应商产能日历可用、人工审批通道可达。任一前置未就绪，
  价格计算就不该被允许开始，而不是算完再报错。这能把"算了一半的报价"这类事故结构性消除。
- **迁移风险**：依赖图容易长成环形（澄清依赖报价、报价依赖澄清）。对策：把循环拆成
  版本化事实 + 单向推进（见设计文档 02 的领域模型状态机）。

## 优势 3：隔离域与配置覆盖，使"同一套能力、多个租户"成为数据问题

- **机制**（`代码` `context.ts:65-77` 的 `isolate`/`intercept`；`loader/src/config/isolate.ts`
  的 `Realm`/`LocalRealm`/`GlobalRealm`；`loader` 条目树按 id diff）。
- **为什么强**：多租户、多环境、多项目不需要分叉代码，改一条 `isolate`/`intercept` 即可；
  且条目可热插拔而配置可被 patch 层覆盖。
- **本领域怎么用**：每个"标段/项目"一个 realm；承包商侧与供应商侧各自的内部服务（标底、
  成本模型、评分）就在各自 realm 内，跨域取不到。**数据主权不是策略声明，而是取不到值的查找失败。**
  行业模板 → 公司策略 → 项目 → 标段，四层 patch 正好对应采购里真实的层级授权。
- **迁移风险**：realm 是命名空间而非安全边界（`[推断]` 论文未声称安全隔离）。**跨组织隔离
  必须落在外层**：不同进程、不同密钥、不同存储，见设计文档 08。

## 优势 4：事件即扩展点，且五种分发模式覆盖全部协作形态

- **机制**（`代码` `events.ts:14`、`events.ts:89-132`）：`emit` 观察、`parallel` 并发扇出、
  `serial` 顺序决策、`bail` 首个有效决策短路、`waterfall` 环绕中间件（不调 `next()` 即短路）。
- **为什么强**：**策略不需要改内核。** 审批、配额、脱敏、合规——全部可以作为监听者插入，
  而且顺序可控（`prepend`）、可短路（waterfall/bail）。
- **本领域怎么用**：比价流水线天然是一个 waterfall：币种/税率/单位归一化 → 技术合规初筛 →
  异常价格检测 → TCO 折算 → 排序。每个环节都可被公司策略层替换或否决，而不动核心逻辑。
  澄清问答用 `serial`（一问一答有先后），通知用 `emit`（不阻塞），投标资格用 `bail`（首个否决胜出）。
- **迁移风险**：waterfall 的短路语义是双刃剑（`代码` `events.ts:117-132`，`next()` 重复调用会抛错）。
  必须像 harness 那样把"不调 `next()` 即短路是设计意图"写成显式规范。

## 优势 5：组成是数据，不是代码——而且运行时改动有明确归属

- **机制**（`代码` `include/src/patch.ts:47-109`、`patch.ts:141-184`、`journal.ts:195-242`）：
  条目树 + patch 层叠加；`PatchIndex` 知道每个键归谁；`reconcile()` 做 base/theirs/journal 三方
  协调，冲突时"文件赢"并上报。
- **为什么强**：**运行时的改动最终能落回文件，且冲突有确定赢家。** 这是 agent 改自己配置却不会与
  人类编辑互相踩踏的机制保证。
- **本领域怎么用**：双方各自持有一本账本（journal 等价物）与一份共识基线；跨方交换时用同类
  三方协调，并声明**每类字段的权威方**（例如：工程量口径归承包商，成本构成归供应商，
  交期承诺归供应商，付款条款归承包商）。冲突不再靠打电话吵架，而是有规则的合并与上报。
- **迁移风险**："文件赢"在跨组织场景要改成"权威方赢 + 留痕"，因为不存在两端都能写的共享文件。
  这条必须新增 ADR（见 ADR-0003）。

## 优势 6：变更收敛到一条可否决的路径（HMR + `internal/update` waterfall）

- **机制**（`代码` `fiber.ts:478-495` + `packages/hmr`）：更新配置先过 `internal/update`
  waterfall，监听者可否决或替换重启；失败被 fiber 捕获（`fiber.ts:417-437`）。
- **为什么强**：**在线改提示词/工具/策略不需要重启会话**，且失败被限制在单个 fiber 内。
- **本领域怎么用**：agent 自进化的执行通道。改一条定价策略、换一个规范解析器、加一条合规检查，
  都应该是"挂在一个条目上、可否决、可回滚、不影响其他 fiber"的操作。这使我们能提出
  "进化只发生在插件层，内核语义不可自改"这条硬约束（AGENTS.md 规则 10）。
- **迁移风险**：`[推断]` 热替换期间的在途状态一致性由 disposer 质量决定；对长事务（跨小时的澄清
  窗口、多轮谈判）需要额外的会话持久化，不能只靠内存 fiber。

## 优势 7：小内核、强约束——内核可被整体理解

- **机制**：`代码` core 六个文件合计 ~1000 行（见 analysis §1），语义集中在一处。
- **为什么强**：**能被完整理解的系统才能被放心地让 agent 改。** 内核小，意味着扩展都发生在
  外围（插件、配置、事件），agent 每次改动的影响半径可估计。
- **本领域怎么用**：我们也把内核限定为四件事：账本（追加式事实）、上下文与插件装载、
  事件分发、协议版本。所有行业逻辑（工程量、成本、税率、条款）都在外围插件里。
- **迁移风险**：无。这是纯粹的取舍——代价是内核能力弱，必须靠外围补齐。

## 优势 8：把"模型可见性"变成可审计的工程约束的土壤

- **说明**：这是我们从 harness 侧提取的工程约定（`docs/analysis/harness-agent-repo-conventions.md`），
  但它的可行性来自 Cordis 的事件/effect 纪律：每一次模型可见输入都可以是一个事件，
  每一次事件注册都是一个 effect，于是"可重建"与"可卸载"能同时成立。
- **本领域怎么用**：招投标场景天然要求可追溯。**任何进入模型输入的事实必须能从账本重建**，
  本身就是审计要求与工程要求的重合点——这是本设计少有的"合规即架构"红利。

## 概念映射表（Cordis → quotagent）

| Cordis 概念 | 机制要点 | quotagent 对应物 |
|---|---|---|
| Context / isolate / intercept | 影子上下文、符号域、配置覆盖 | 参与方/项目/标段上下文；数据主权边界 |
| Fiber | 一个插件实例的生命周期与副作用集合 | 一个 agent 能力实例（读包、算价、比价、澄清） |
| revertible effect | 注册即交出 disposer，卸载逆序回收 | 本地状态/订阅/定时器/草稿；**不含对外承诺** |
| reactive coeffect (`inject`) | epoch 比较触发激活/失活 | 报价前置条件图（RFQ 冻结、汇率、产能、审批通道） |
| typed events + `@mode` | emit/parallel/serial/bail/waterfall | QEP 生命周期事件；比价与合规流水线 |
| Service / Registry | 服务提供与依赖解析，同名多实例 | 能力 seam：Definition/Provider/Consumer 三角 |
| loader 条目树 + group | 按 id diff 的声明式组成 | 项目采购流程的可编辑配置 |
| patch / journal / reconcile | 三方协调、归属路由、冲突上报 | 双方账本同步与字段权威方仲裁 |
| HMR + internal/update waterfall | 可否决的在线更新 | agent 自进化的晋升通道 + 人工否决点 |
| profiles / bundles | 分层装配与分发 | 行业模板 / 公司策略 / 项目 / 标段 四层 |
| 状态机 + inertia | 生命周期串行化，不并发打架 | 澄清窗口与多轮谈判的会话状态一致性 |

## 一句话结论

Cordis 值得发扬的不是某个 API，而是它的**三条纪律**：副作用必须可回退、依赖必须可声明并被
响应式协调、系统组成必须是可以被编辑和协调的数据。把这三点移植到跨组织的采购报价场景，
需要补上 Cordis 天生不覆盖的一环——**不可回退的对外承诺如何治理**（ADR-0004）。
